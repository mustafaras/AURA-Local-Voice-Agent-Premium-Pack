## Result 1 — the original denial is GONE, and the confirmation card appears

This is the finding this record exists for. Driving the installed app through
the accessibility API: gear → Settings → the *Girişte AURA'yı başlat* toggle.

**Before the fix** (`EV-SP-030-20260831-R11-POLICY-BLOCK-01`, this morning):

```
Permission denied: No matching grant and tier mutation is denied by default
```

**After the fix**, the confirmation card is rendered in the AURA window:

```
TXT [ONAY GEREKLİ]
TXT [lifecycle.launchAtLogin]
TXT [any]
TXT [Risk: 2 · Bitiş 8/31/2026, 15:26]
```

and, when the card is left unanswered until it expires, the detail reads:

```
Permission denied: lifecycle.launchAtLogin was not confirmed
```

That string is the **new** message introduced by the fix. Its appearance is
decisive on two counts, and neither is inferred from source:

1. **Layer 1 is open.** The request no longer dies at "no matching grant"; the
   seeded grant matches and evaluation now reaches `.confirm`.
2. **Layer 2 is open.** A challenge was created *and presented* — the card is on
   screen, naming the capability, its `any` target, its risk tier and its
   expiry. Before the fix this path threw without presenting anything.

The card also confirms the grant's `.forRiskTier(.mutation)` posture behaves as
intended: `Risk: 2` is `.mutation`, and the user is asked rather than silently
allowed.

## Result 3 — why the failure was invisible: a silent-failure defect

Chasing Result 2 surfaced a second real defect, in code that predates today.

```swift
func refreshLaunchAtLogin() {
  … launchAtLoginDetail = ""            // clears on success
}

func setLaunchAtLogin(_ enabled: Bool) {
  … catch {
    launchAtLoginDetail = error.localizedDescription   // writes the reason
    refreshLaunchAtLogin()                             // …then erases it
  }
}
```

The failure path records why the toggle failed and then immediately calls a
re-read whose success branch overwrites that message with an empty string. The
user sees the toggle snap back **with no explanation**. The `catch` in
`refreshLaunchAtLogin` carries the comment *"Reported, never swallowed: a silent
false here would read as 'disabled' when the truth is 'could not be
determined'"* — and the caller does exactly the swallowing that comment warns
against.

*Fixed:* `refreshLaunchAtLogin(preservingDetail:)` carries the reason through
the re-read. Suite stays **1320 tests / 86 suites / 22 bundles, 0 failures**.

## Result 4 — an open design consequence, NOT fixed, for the owner

`isLaunchAtLoginEnabled()` — a **read** — is gated by the *same*
`.mutation`-tier `lifecycleLaunchAtLogin` capability as the write
(`AuraKernel_RuntimeAPI.swift:678`). With `confirmationRequirement:
.forRiskTier(.mutation)`, every read requires its own confirmation. So:

1. opening Settings fires `.onAppear` → `refreshLaunchAtLogin()` → **a card**;
2. flipping the toggle → **a second card**;
3. any failure → re-read → **a third card**.

Cards expire after 60 s, so they queue and lapse, and a user answering one may
be answering a different request than they think. This is a plausible
contributor to Result 2 and is a **design question, not a bug to patch
silently**. Two candidate directions, neither taken:

- **A separate observation-tier capability for the read.** Correct in principle
  — reading whether a login item exists is not a mutation — but it adds a
  capability and changes the policy surface.
- **`confirmationRequirement: .oncePerSession`.** Much smaller; the user
  confirms once per session and subsequent reads and writes proceed. Weaker per
  action than `.forRiskTier(.mutation)`.

Both change the authorization posture, so both need the owner, exactly as the
original grant did.

## Environment note for future sessions

Every AURA window — the main panel **and** `AURA Settings` — dismisses when the
app loses focus, and `osascript` itself takes focus. Any AX query issued as a
*separate* invocation therefore sees `windows = 0` or fails with `-1728` /
`Invalid index`. The working pattern is: `tell application "AURA" to activate`,
then do **everything** inside that one `osascript` call. Also: `entire contents
of window "X"` used inline fails with *"into type specifier"* — assign it to a
variable first; AX element references cannot be accumulated into an AppleScript
list; SwiftUI buttons expose **no** AX title (all read `description = "button"`),
so they must be addressed by position; and `click at {x,y}` is refused with
`-25211` (osascript lacks that grant) while clicking AX *elements* works.

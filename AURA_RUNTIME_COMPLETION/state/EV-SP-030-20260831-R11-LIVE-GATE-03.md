## The defect being fixed

A policy confirmation raised by a control in `AURA Settings` was rendered only
inside the **main panel**. Every AURA window dismisses when the app's focus
moves, so a user toggling *Girişte AURA'yı başlat* was asked to authorize in a
window they were not looking at. The 60 s challenge lapsed unanswered and the
write failed with `Permission denied: lifecycle.launchAtLogin was not
confirmed`.

## What was implemented

**1. The card renders inline as the first row of the Settings form.**
`AuraSettingsView`'s `Form` now begins with `AuraConfirmationCard` whenever
`model.pendingConfirmation` is non-nil, so the authorizing surface lives in the
window that requested the action and is on screen without scrolling.

**A `.sheet` was tried first and rejected on evidence, not taste.** Attached
inside SwiftUI's `Settings` scene it did not present at all: the installed build
showed `Confirmation required: lifecycle.launchAtLogin` in the model's status
line while the Settings window reported `sheets=0` and no card anywhere in its
accessibility tree. Shipping it would have reintroduced the *same*
invisible-confirmation bug in a new form. The inline row is used precisely
because it cannot silently fail to appear.

**2. Closing Settings with a confirmation pending now fails closed.**
`AuraAppModel.denyConfirmationIfStillPending()`, called from `.onDisappear`,
denies rather than leaving the challenge to lapse. The rule is a named model
method, not logic buried in a view binding, so it is testable — and the ordering
matters: answering through the card clears `pendingConfirmation` *first*, so the
dismissal path finds nothing to do and cannot overturn an authorization the user
just granted.

## What is NOT verified — stated plainly

**The live run was not performed.** After the install, the machine's display
powered off (`ioreg` reports the display unpowered; `screencapture` fails with
`could not create image from rect`; the accessibility tree reports `windows = 0`
for a healthy process). The display cannot be woken programmatically, and
nothing here should be taken as evidence that it was.

So this record claims exactly one thing: **the code path that made the
confirmation invisible is changed, and the change is covered by tests.** It does
**not** claim that:

- the card is visibly rendered in the Settings window on the running app;
- a user can accept it;
- `SMAppService` is reached or a login item is registered;
- the toggle reads back enabled;
- any of it survives a reboot.

**R11's live gate remains NOT CLOSED, and launch-at-login is not known to
work.** The `deterministic_harness` result is a strong signal and it is not the
live gate. The next session must re-run the live sequence with the display
awake: gear → Settings → toggle → the card should now appear **in the Settings
window** → accept → the toggle should read back enabled → confirm the login item
in System Settings › General › Login Items → reboot.

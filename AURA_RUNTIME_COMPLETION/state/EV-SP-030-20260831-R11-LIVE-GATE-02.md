## Verified live — two fixes confirmed on the installed app

**1. Opening Settings no longer prompts.** Observed directly:

```
on Settings open: NO CARD
```

Before the split, `.onAppear` → `refreshLaunchAtLogin()` → a `.mutation`
confirmation. That prompt is gone, and the write still confirms. This is the
Result 4 fix working.

**2. The failure reason now persists instead of being erased.** After toggling,
the Settings pane shows:

```
[Girişte AURA'yı başlat]
[AURA'yı ServiceManagement ile macOS Giriş Ögeleri'ne kaydeder.]

```

Under LIVE-GATE-01 this line came back **empty**, because `setLaunchAtLogin`'s

is the Result 3 fix working — and it is what made the remaining blocker
diagnosable at all.

## The remaining blocker, now identified

`BEFORE=0` → click → `AFTER=0`, with
`Permission denied: lifecycle.launchAtLogin was not confirmed`.

That message is precise and rules out the earlier suspects. The write **does**
fire, **does** match the grant, **does** reach `.confirm`, and the presenter
**is** invoked. What fails is the last step: the confirmation is never answered.

The confirmation card is rendered inside the **main AURA panel**, not in the
`AURA Settings` window that initiated the action. Every AURA window dismisses
when the app's focus moves, so while the user is in Settings the panel holding
the card is not in front of them. The challenge then expires on its 60 s timer
and the write fails. Raising the main window programmatically (`AXRaise`) did
not surface the card either, so its visibility depends on panel state —
including which tab is selected — rather than on the pending confirmation alone.

**This is a product defect, not an artifact of the automation.** A real person
clicking *Girişte AURA'yı başlat* in Settings is asked to confirm in a window
they are not looking at, and the toggle fails with a message they must scroll
the Settings pane to find. It is exactly the class of defect a live gate exists
to catch and that no unit test would have found — the suite stands at 1322
passing tests with this present.

**Not fixed here.** Where a policy confirmation should be presented — a sheet on
the initiating window, an app-modal alert, or a panel that cannot be dismissed
while a challenge is pending — is a UI architecture decision with security
consequences (a confirmation the user cannot see must never be auto-answered),
and it belongs to the owner, like the two decisions before it.

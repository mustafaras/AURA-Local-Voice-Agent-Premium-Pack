# ADR-021 — Intent Engine and Tool Router

- Status: Accepted
- Date: 2026-07-27
- Owners: Claude Sonnet 5 (Claude Code)
- Supersedes: —
- Superseded by: —

## Context

Phases 0–19 each built one AURA subsystem in isolation with real unit/contract tests, but nothing decided what a completed conversational turn should actually *do*. `Conversation` (Phase 4) emits `TurnCompletedEvent` on a stable transcript and waits to be handed a `ResponsePlanEvent` via its `responsePlanReceived(_:)` method — but before this phase, nothing subscribed to the former and nothing produced the latter (confirmed by reading `Sources/AuraAgent/Conversation.swift` in full: `Conversation` never calls `eventBus.subscribe` itself, and `grep`ing the repository found zero references to `TurnCompletedEvent` outside `Conversation`/its own tests). `docs/subsystems/08_INTENT_ENGINE.md` and `09_TOOL_ROUTER.md` are normative specs with no implementing code at all — confirmed by a full-repository search for "Intent"/"ToolRouter"/"IntentEngine"/"Dispatch" identifiers, which found only `ComputerUseSemanticIntent` (an unrelated enum) and the English word "intent" in comments.

Meanwhile, every backend subsystem this phase needs to dispatch to already exists and is real: `PolicyEngine` (Phase 5), `AuraAutomation` (Phase 6), `AuraShell` (Phase 7), `AuraTaskEngine` (Phase 9), and the Codex/Claude/Copilot CLI adapters (Phases 10–12), each already policy-gated and tested. This ADR covers the new decision layer built between them.

## Decision

1. **A new `AuraIntent` library target**, depending on `AuraCore`, `AuraPolicy`, `AuraShell`, `AuraAutomation`, `AuraAgent`, `AuraTasks`, `AuraContext` — following the established one-target-per-materially-new-subsystem precedent. It has no dependency on `AuraAudio`/`AuraSTT`: intent classification operates on already-transcribed text (`TurnCompletedEvent.text`), never on audio.

2. **A deliberately small, closed v1 vocabulary — `IntentKind`: `converse`, `appActivate`, `appTerminate`, `shellExecute`, `codingAgentRun`, `unknown`** — rather than attempting all ten intent classes `08_INTENT_ENGINE.md` lists (Application command, File/workspace command, Coding-agent command, Browser task, Observation request, System setting, Memory operation, High-risk external action, plus Conversation and Unknown). Each of the five real kinds maps to a backend this phase can genuinely wire (`AuraAutomation`, `AuraShell`, the CLI adapters); the remaining five (VS Code, screen/computer-use, memory operations, browser tasks, and any high-risk external action beyond destructive shell) are explicit, named future work — adding their dependencies now, before any classifier or handler exists for them, would be unused scope. `TypedIntent` (`Sources/AuraIntent/TypedIntent.swift`) is a closed struct — `kind: IntentKind`, `semanticCategory: IntentSemanticCategory`, and named `IntentSlot`s (never a raw free-text command string reaching execution) — mirroring `ComputerUseActionStep`'s "closed schema, never raw string eval" precedent (`Sources/AuraComputerUse/ComputerUseControlLoop.swift`) at the intent layer.

3. **`riskTier` and `requiresMandatoryConfirmation` are always derived from `semanticCategory` at `TypedIntent` construction, never independently supplied** — `IntentSemanticCategory` (`Sources/AuraCore/IntentPolicyTypes.swift`) is a pure, non-negotiable mapping, mirroring `ComputerUseSemanticIntent`'s own precedent exactly. `IntentSemanticCategory.mandatoryConfirmationCategories` currently contains only `.shellDestructive` — a closed `Set` constant, not a configuration field, matching `ComputerUseSemanticIntent.mandatoryConfirmationIntents`'s own "not something a `Grant`'s `confirmationRequirement` should be able to relax" reasoning (ADR-019 decision 4).

4. **`RuleBasedUtteranceClassifier` (`Sources/AuraIntent/IntentEngine.swift`) is deterministic and model-free: closed keyword-prefix rules plus two small, explicit lookup tables** (app name → bundle identifier; shell executable name → absolute path). An utterance that matches a command *shape* (e.g. "activate X") but names something outside its table is classified `.unknown` with confidence `0.3`, carrying the unresolved name as a slot — **never a guessed bundle identifier or executable path**. This is the concrete mechanism behind "may select among registered tools, never invent one" (`08_INTENT_ENGINE.md`). `UtteranceClassifying` is a protocol specifically so a future NLU/LLM-backed classifier can replace this one without changing `IntentEngine`, `ToolRouter`, or the `TypedIntent` schema — only ever the speed/accuracy of filling that fixed schema changes, never what the schema permits.

5. **`IntentEngine.classify` forces `.unknown`/`isAmbiguous` when the classifier's confidence is below `IntentEngineConfiguration.minimumClassificationConfidence` (default `0.6`)** — a single, config-driven gate applied uniformly regardless of which rule matched, implementing `08_INTENT_ENGINE.md`'s "calculate ambiguity/risk" step as one deterministic check rather than per-rule ad hoc thresholds.

6. **`ToolRouter` (`Sources/AuraIntent/ToolRouter.swift`) encodes a real architectural split discovered while wiring it, not papered over uniformly: some backends already evaluate their own policy, others don't.** `CodexAdapter`/`ClaudeAdapter`/`CopilotAdapter` already call `PolicyEngine.evaluate` internally before running (confirmed in each adapter's source). `AuraAutomation`'s own doc comment says it "does not enforce policy itself," and `AuraShell.execute`'s own doc comment says it "constructs [a policy request] but does not enforce" it. `ToolContract.enforcesPolicyInternally` (new field, not in `09_TOOL_ROUTER.md`'s literal spec text) makes this split explicit: `ToolRouter` evaluates policy itself for `.appActivate`/`.appTerminate`/`.shellExecute` (`enforcesPolicyInternally: false`) and never does for `.codingAgentRun` (`enforcesPolicyInternally: true`) — delegating wholesale to the wrapped CLI adapter's own internal check.

7. **A `.codingAgentRun` intent is enqueued via `AuraTaskEngine` and never awaited — `ToolRouter.handleCodingAgentRun` returns `.acknowledgedAsync` as soon as `enqueue` succeeds.** `ConversationConfiguration.thinkTimeoutSeconds` (default 30s, documented as "seconds allowed for the intent engine to produce a response plan") bounds how long `IntentDispatchCoordinator` can take to produce a `ResponsePlanEvent`; a real coding-agent CLI turn routinely takes far longer. `CodexTaskRunner`/`ClaudeTaskRunner`/`CopilotTaskRunner` (Phases 10–12) already exist specifically to run a CLI-adapter turn as a durable, checkpointed `AuraTaskEngine` task — reused directly, not reimplemented.

8. **`AgentBackendTaskRunner` (`Sources/AuraIntent/AgentBackendTaskRunner.swift`) is a single `TaskRunner` multiplexing Codex/Claude/Copilot by a `TaskRequest.context` key — not three separate runner instances.** This is structurally required, not a style preference: reading `Sources/AuraTasks/AuraTaskEngine.swift` found that `enqueue(request:runner:)`/`start(runner:)` both pump the shared priority queue with whatever `runner` was passed to *that specific call*, and `pumpQueueAsync` dequeues *whatever task is next* in the queue — not necessarily the one enqueued alongside that runner. Passing three different runner instances across different `enqueue` calls would risk a task enqueued for one backend being executed with a different backend's runner. `AgentBackendTaskRunner` is the only runner `AuraKernel`/`ToolRouter` ever pass to `AuraTaskEngine`, eliminating the hazard by construction rather than by caller discipline. `AuraTaskEngine` itself was not modified — this is a real, load-bearing constraint of its existing, already-shipped design, worth a future look but out of scope here.

9. **The mandatory-confirmation guard is checked unconditionally after receiving `.allow` from `PolicyEngine`, regardless of whether that `.allow` came directly from a grant or from a genuine confirm-then-allow round trip** — mirroring `ComputerUseControlLoop`'s placement of `step.semanticIntent.requiresMandatoryConfirmation` immediately after `policyEngine.evaluate` returns `.allow` (`ComputerUseControlLoop.swift:280`, ADR-019 decision 4). Unlike `ComputerUseControlLoop` (which halts and returns an unresolved challenge to its own caller on `.confirm`, since it has no injectable presenter), `ToolRouter` follows the CLI-adapter precedent instead (`CodexAdapter`'s `approvalPresenter` pattern): on `.confirm`, it presents the challenge via an injected `IntentConfirmationPresenting` and calls `PolicyEngine.submitConfirmation` itself, since a router dispatching short, single actions is closer in shape to a CLI adapter's one-shot run than to a bounded multi-step loop needing external resolution. The production default, `IntentAlwaysDenyConfirmationPresenter`, mirrors `CodexAlwaysDenyApprovalPresenter`'s doc comment precisely: a real implementation would surface a voice/UI confirmation and only echo the accepted response after genuine user consent; no such surface exists yet, so any capability landing on `.confirm` is refused by default. Regardless of which path led to `.allow`, `.shellDestructive` (the one `mandatoryConfirmationCategories` member) is *still* blocked — proven by a dedicated test (`routerBlocksDestructiveShellPatternEvenWithPermissiveGrant`) that seeds an explicit `.none`-confirmation grant for both `.shellExec` and `.shellExecDestructive` and shows the step is still refused.

10. **Destructive-shell detection is a conservative, explicit regex denylist checked against already-parsed, already-typed slots (executable + arguments) — never a raw string `eval`, and explicitly defense-in-depth, not the primary safety mechanism.** `IntentEngineConfiguration.destructiveShellPatterns` defaults to four patterns (`rm -rf`-style flag combinations, `diskutil erase/reformat/partitionDisk`, `dd ... of=/dev/`, a literal fork-bomb signature). A match escalates `semanticCategory` from `.shellExecute` to `.shellDestructive` via `TypedIntent.escalated(to:)`, which recomputes `riskTier`/`requiresMandatoryConfirmation` from the new category — never a manually-set flag that could drift out of sync with what the category actually implies. The primary mechanism is unconditional: plain `.shellExecute` already defaults to `.always` confirmation (see ADR-022's grant table), so an unrecognized destructive command is still gated, just without the extra escalation signal.

## Alternatives considered

- **Covering all ten `08_INTENT_ENGINE.md` intent classes in v1.** Rejected — see decision 2; no backend exists yet for five of them, and building classifier rules with no real dispatch target would be dead code.
- **A model-based (LLM) classifier for v1.** Rejected — deterministic rules are fully reproducible in tests, have no network/model dependency, and the `UtteranceClassifying` protocol seam means this can be revisited later without touching anything downstream.
- **Guessing a bundle identifier/executable path for an unrecognized name** (e.g. via fuzzy matching or a heuristic path search). Rejected — see decision 4; a wrong guess executed against a real application or binary is a worse failure mode than an honest `.unknown` classification the user can clarify.
- **Awaiting the coding-agent CLI run synchronously in `ToolRouter.handleCodingAgentRun`.** Rejected — see decision 7; would routinely exceed `Conversation`'s think-timeout and self-transition the turn to `.timeout` before the agent finished.
- **Three separate `TaskRunner` instances (one per backend) passed to different `enqueue` calls.** Rejected — see decision 8; structurally hazardous given `AuraTaskEngine`'s actual pump/dequeue behavior.
- **Having `ToolRouter` halt and return an unresolved challenge on `.confirm`, matching `ComputerUseControlLoop` exactly.** Rejected — see decision 9; no mechanism yet exists for a clarifying "please confirm" reply to loop back into a resolved confirmation via voice, so the CLI-adapter-style inject-a-presenter pattern is the implementable choice for this phase.
- **No destructive-shell pattern detection at all — rely solely on `.always` confirmation for every shell command.** Rejected — see decision 10; the extra escalation signal is cheap, real defense-in-depth, and consistent with this project's layered-mitigation precedent (ADR-018 decision 7's "two independent off-switches").

## Security and privacy impact

- No raw utterance text or free-text command ever reaches a backend subsystem directly — only closed-enum `IntentKind`/`IntentSemanticCategory` values and named `IntentSlot`s, matching the project's "raw model output must never be executed directly" rule at the intent layer.
- Every router-enforced branch (`appActivate`/`appTerminate`/`shellExecute`) is denied by default absent an explicit grant, and `.shellDestructive` can never execute on a bare `.allow` regardless of grant configuration.
- `IntentBlockedEvent`/`IntentClassifiedEvent`/`IntentPlanGeneratedEvent`/`ToolInvokedEvent`/`ToolResultEvent` (`Sources/AuraCore/IntentEventPayloads.swift`) give a full, typed audit trail of every classification and dispatch decision; `ToolResultEvent.summary` is a bounded, human-readable string, never raw command output.
- An unresolved app name or executable is always surfaced as an `.ambiguous` clarifying question, never silently acted on.

## Operational impact

- New library target `AuraIntent` and test target `AuraIntentTests` added to `Package.swift`.
- `Sources/AuraCore/` gains `IntentPolicyTypes.swift`, `IntentEventPayloads.swift`, new `Capability.intentConverse`/`.shellExecDestructive` statics plus `Capability.forIntent(_:)`, a new `ActorID.intent` case, and a new `IntentEngineConfiguration` nested inside `AuraConfiguration`.
- No existing subsystem's public API changed except `AuraConfiguration` (additive field) and `ActorID`/`Capability`/`AuraError` (additive cases) — all backward compatible.
- `AuraTaskEngine`'s single-global-runner behavior was not changed; `AgentBackendTaskRunner` works around it at the call-site level, per decision 8.

## Migration

No breaking migration. No new database tables. Existing `AuraConfiguration` JSON files decode unchanged; a missing `intent` key merges in `IntentEngineConfiguration()`'s defaults exactly like every other nested configuration struct.

## Validation evidence

- `swift build` (full workspace, fresh path) — zero errors, zero non-linker warnings.
- `AuraIntentTests`: 22/22 pass — `RuleBasedUtteranceClassifier` cases for every `IntentKind` including both `.unknown` paths (unresolved app name, unresolved executable); `ToolRouter` cases covering ambiguity short-circuit (never touches policy), converse (never touches policy), app activate/terminate (granted, denied, confirmation-denied, automation-throws), shell execute (non-destructive granted, destructive blocked even with a permissive grant, destructive denied-by-default under a fully permissive tier configuration), and coding-agent run (acknowledged promptly without the router itself evaluating policy, unsupported backend rejected). Re-run 3× across separate fresh build paths with no flakiness.
- See ADR-022 for the end-to-end (`AURAIntegrationTests`) evidence exercising this decision layer as part of the full wake→STT→intent→policy→tool→response→TTS chain.

## Consequences

- Positive: the single biggest missing piece blocking any end-to-end AURA behavior — deciding what a completed utterance should cause the assistant to do — now has a real, tested, evidence-backed implementation.
- Positive: the router-enforced/adapter-self-enforced policy split and the mandatory-confirmation guard's placement are now explicit, documented architecture rather than something a future maintainer would have to rediscover by reading five different adapters' source.
- Limitation: only five intent kinds are real; `08_INTENT_ENGINE.md`'s other five (and a real NLU/LLM classifier) remain deliberately deferred, tracked as Stage 3 follow-up work in `docs/decisions/ADR-022-composition-root-wiring.md`.
- Limitation: `ContextEngine.resolveReference` (Phase 16) is threaded through `IntentEngine`'s initializer but not yet used by any v1 rule — pronoun/reference resolution ("open it," "quit that") is not implemented in this phase.
- Limitation: `IntentConfirmationPresenting`'s production default denies every confirmation-requiring action, since no real voice/UI confirmation surface exists yet — a capability landing on `.confirm` today always resolves to "not done," never to a genuine user answer.

# ADR-012 — Claude Code CLI Adapter Architecture

- Status: Accepted
- Date: 2026-07-25
- Owners: Claude Sonnet 5 (Claude Code)
- Supersedes: —
- Superseded by: —

## Context

Phase 11 of the AURA implementation roadmap requires integrating the Claude Code CLI as a durable, policy-gated tool adapter: verified interfaces, permission mapping, hooks safety, session events, budgets, and integration tests — the same acceptance bar ADR-011 set for the Codex adapter. This phase deliberately reused Phase 10's architecture (single-continuation adapter actor, `AdapterProcessExecuting` seam, `TaskRunner` conformance, upfront-policy-gate-not-mid-run-prompt design) rather than re-deriving it, since the two CLIs are structurally similar non-interactive coding-agent backends. Several facts discovered during implementation diverge from Codex's and from this phase's own initial assumptions, and are recorded here because they materially shaped the design:

1. **`claude -p` (non-interactive/"print" mode) has a real, working `--permission-mode dontAsk`.** Unlike `codex exec` (which has no approval flag at all — ADR-011), Claude Code's CLI does expose an explicit headless-safe permission mode. Official documentation states plainly: "`dontAsk` denies anything not in your `permissions.allow` rules or the read-only command set... For unattended CI, `dontAsk` is the only safe choice." `AskUserQuestion`, org-restricted connector tools, and MCP tools marked `requiresUserInteraction` are denied even when an allow rule matches — so `dontAsk` genuinely never blocks waiting on input that cannot arrive.
2. **`--bare` (the officially documented, recommended mode for scripted/CI calls — "will become the default for `-p` in a future release") does not work in this deployment's authentication mode.** `--bare` skips OAuth and keychain reads; Anthropic auth must come from `ANTHROPIC_API_KEY` or an `apiKeyHelper` passed via `--settings`. This machine's `claude` CLI is authenticated via ChatGPT/Claude subscription through the keychain (confirmed: no `ANTHROPIC_API_KEY` env var, no local `~/.claude/.credentials.json`, and the real smoke test's `system/init` event reported `"apiKeySource":"none"`). `--bare` would therefore fail to authenticate for any AURA user on subscription auth — likely the common case, not an edge case. `--setting-sources user` was used instead: it excludes `project`/`local` settings layers (where a target repository's own `.claude/settings.json`/`settings.local.json` configures hooks and `.mcp.json`-referenced servers) while leaving the operating user's own trusted `~/.claude/settings.json` — and OAuth/keychain auth — untouched. The real smoke test confirms this: a `SessionStart` hook from the *user's own* config still ran (`hook_started`/`hook_response` events), while no project-level hook could have run since the working directory had no such settings file to exclude in the first place. This is the same hooks-safety goal `--bare` targets, achieved without the auth regression.
3. **`claude -p` requires the prompt as a positional CLI argument — there is no stdin-only prompt mode.** Unlike `codex exec` (`[PROMPT]`, "read from stdin" when omitted), Claude Code's documented pattern is `cat data.txt | claude -p "instruction"`: piped stdin is supplementary data alongside a required instruction, not a replacement for it. Passing a free-text objective (which routinely contains `;`/`|`/`&&`) as that positional argument would fail `Command.validate()`'s metacharacter check, the same problem ADR-011 solved for Codex via `Command.standardInputText` alone. Here, that mechanism alone is insufficient; the fix combines it with a fixed, harmless positional wrapper prompt (`claudeWrapperPrompt`, `Sources/AuraAgent/ClaudeArguments.swift`) — `"Follow the objective provided via standard input, then respond accordingly."` — while the real objective is delivered entirely through `Command.standardInputText`. **This was verified, not assumed**: the authorized smoke test's piped stdin content (`"Reply with exactly one word: ping"`) is exactly what the model acted on, confirming Claude Code treats piped stdin as operative content even when the visible CLI prompt is only a generic wrapper.
4. **`--max-budget-usd` gives real, CLI-native cost enforcement** — a capability Codex's CLI has no equivalent of (ADR-011's token/cost budget is advisory-only for that reason). Claude Code enforces the dollar cap itself; the adapter only needs to pass the flag and, post-hoc, compare the CLI's own reported `total_cost_usd` against the configured budget for observability (see Decision 6).
5. **JSONL field casing is inconsistent within the same payload**, confirmed by the real smoke test: `session_id`/`total_cost_usd`/`hook_name`/`claude_code_version` are snake_case while `permissionMode`/`apiKeySource`/`modelUsage`/`rateLimitType` are camelCase — sometimes both conventions appear in the *same* event object (`system`/`init`: `session_id` next to `permissionMode`). `ClaudeEventNormalizer` maps every field explicitly via `CodingKeys` rather than assuming one global casing convention or using `keyDecodingStrategy = .convertFromSnakeCase`, which would have silently mis-decoded the camelCase fields.
6. **`tool_use`/`tool_result` JSONL shapes were never observed.** The authorized smoke test ran with `--tools ""` (confirmed via the real `system/init` event: `"tools":[]`) specifically to keep the call minimal, harmless, and side-effect-free — so no tool-call content block was ever produced to inspect. Per AGENTS.md, these shapes are not fabricated: `ClaudeEventNormalizer` decodes only the confirmed `text` content-block type and carries anything else (`.unclassifiedContent`) opaquely. A direct consequence: **there is no live file-write budget enforcement for the Claude adapter** (unlike Codex's file-change counting) — implementing one would require guessing at unobserved field names for detecting write-capable tool calls. Instead, `.readOnly` tool profile prevents writes by construction: `--tools "Read,Grep,Glob"` means no write-capable tool exists in that tier at all, a stronger guarantee than post-hoc counting. `ClaudeConfiguration` has no `maxFileWritesPerRun` field for this reason — an unenforceable config field would itself be a form of placeholder/dead code.

## Decision

1. **Reuse Phase 10's plumbing; generalize the one seam that was Codex-specific.** `AuraShell.executeStreaming`/`ProcessRunner.runStreaming`/`Command.standardInputText` are used unmodified. `CodexProcessExecuting`/`ShellCodexProcessExecutor` were renamed to `AdapterProcessExecuting`/`ShellAdapterProcessExecutor` (`Sources/AuraAgent/AdapterProcessExecuting.swift`) and both `CodexAdapter` and `ClaudeAdapter` now depend on the shared protocol — this is the second adapter needing the identical seam, so sharing it is a genuine reduction in duplication, not a premature abstraction. The working-directory allowlist check (`requireAllowed`/`expandPathVariables`) was likewise extracted into `Sources/AuraAgent/WorkingDirectoryAllowlist.swift` and both `CodexArguments` and `ClaudeArguments` now call it instead of each keeping a private copy.
2. **`--permission-mode dontAsk` is always present and never derived from any parameter**, exactly mirroring Codex's `-a never` hardcoding — even though Claude's CLI *does* have other non-interactive-plausible-looking modes (`acceptEdits`, `auto`), `dontAsk` is the only one documented as CI-safe; the others either still prompt for uncovered actions (blocking forever with no TTY) or (for `bypassPermissions`) skip checks entirely.
3. **`--dangerously-skip-permissions`/`--allow-dangerously-skip-permissions` never appear** — structurally absent from `ClaudeArguments.make`, not merely avoided by convention, mirroring Codex's forbidden bypass flag.
4. **Two Claude-specific capabilities**, `Capability.agentClaudeReadOnly` (`.reversible`) and `Capability.agentClaudeRun` (`.destructive`), added to `PolicyTypes.swift` following the existing per-domain pattern rather than reusing the generic `Capability.agentRun` or Codex's capabilities — grants/denies can target each backend independently.
5. **Tool profile, not sandbox tier, is the AURA-facing abstraction**, since Claude Code's model is tool-name-based rather than filesystem-sandbox-based: `ClaudeToolProfile.readOnly` maps to `--tools "Read,Grep,Glob"` (configurable via `ClaudeConfiguration.readOnlyTools`) and `.workspaceWrite` to `--tools "Bash,Read,Edit,Write,Grep,Glob"` (`workspaceWriteTools`). There is no profile granting "all built-in tools" or an escape hatch to `--dangerously-skip-permissions` — unreachable by construction, matching Codex's unreachable `danger-full-access`.
6. **Budgets**: time is enforced for free by the existing `ProcessRunner` deadline loop (unchanged from Codex). Cost is enforced natively by the CLI via `--max-budget-usd` (`request.maxCostUSD ?? configuration.maxEstimatedCostUSD`); `ClaudeAdapter` additionally performs a post-hoc comparison of the CLI's own reported `total_cost_usd` against the same budget and emits `ClaudeBudgetExceededEvent`/`.budgetExceeded` for observability (the run has already finished by the time the final cost is known, so this is audit signal, not pre-emptive cancellation — genuinely different from Codex's live file-write cancellation, and documented as such rather than implying parity it doesn't have). File writes are not tracked (see Context §6).
7. **Process-level failure is surfaced even when Claude never gets to write a `result` line** — identical reasoning and mechanism to ADR-011 Decision 7: `ClaudeAdapter.perform` inspects every `.completed(ProcessResult)` and yields a synthesized `.turnFailed` whenever the process was cancelled, timed out, or exited unexpectedly.
8. **`ClaudeEventNormalizer` decodes only confirmed shapes**, each field mapped through explicit `CodingKeys` (see Context §5), with generic `JSONSerialization`-based array-length extraction (`tools`, `mcp_servers`, `permission_denials`) used only where element shape is unconfirmed — the same lenient-extraction pattern ADR-011 used for Codex's `usage` object.
9. **`ClaudeTaskRunner: TaskRunner` requires zero `AuraTasks` changes**, reading working directory/tool profile from `TaskRequest.context`'s existing free-form dictionary — identical mechanism to `CodexTaskRunner`.
10. **`--resume`/`--continue` (multi-turn session persistence) is explicitly out of scope** for this phase — `ClaudeRunRequest` has no `resumeSessionID` field, matching Codex's `codex exec resume` scoping decision.
11. **`--include-partial-messages`/token-level streaming is out of scope.** The adapter consumes complete JSONL lines (one event per line); live token-by-token text deltas (`stream_event`/`text_delta`, documented but not required for tool-call/completion-level orchestration) are a named follow-up, not implemented here.

## Alternatives considered

- **Default to `--bare`.** Rejected once auth verification showed it would break OAuth/keychain-authenticated deployments (see Context §2) — `--setting-sources user` achieves the same hooks-safety goal without the auth regression.
- **Deliver the objective as the positional prompt directly.** Rejected — fails `Command.validate()`'s metacharacter check for ordinary free-text objectives, the same problem ADR-011 solved differently for Codex (stdin-only was sufficient there; Claude requires a positional argument regardless, hence the wrapper-prompt approach).
- **Fabricate `tool_use`/`tool_result` field shapes to implement live file-write budget enforcement**, mirroring Codex's `file_change` item counting. Rejected per AGENTS.md's "never fabricate" rule — the smoke test intentionally ran with `--tools ""` to stay minimal and harmless, so these shapes were never observed. Tool-existence restriction via `--tools` is used instead, which is a *stronger* guarantee (no write-capable tool exists in the read-only tier) than post-hoc counting would have been anyway.
- **Keep `CodexProcessExecuting` Codex-specific and duplicate it as `ClaudeProcessExecuting`.** Rejected — identical shape, zero variation needed; generalizing to `AdapterProcessExecuting` (Decision 1) is a straightforward, low-risk deduplication now that a second adapter needs the exact same seam, not a speculative abstraction for a hypothetical future one.
- **Use `keyDecodingStrategy = .convertFromSnakeCase` for the whole normalizer.** Rejected — would silently mis-decode the camelCase fields observed in the same real payloads (Context §5); explicit per-field `CodingKeys` was used instead.

## Security and privacy impact

- The Claude objective is delivered via stdin and deliberately excluded from the `PolicyEvaluationRequest` target/audit summary (`ClaudePolicyAdapter`), matching `CodexPolicyAdapter`.
- `--setting-sources user` prevents a target repository's own hooks (privileged shell commands, per `docs/subsystems/18_CLAUDE_CONTROLLER.md`: "Treat hooks as privileged code because they execute with user permissions") from ever running under an AURA-driven invocation, without disabling the operating user's own trusted configuration.
- `--dangerously-skip-permissions`/`--allow-dangerously-skip-permissions` are structurally unreachable.
- `--add-dir` targets and the working directory are validated against `ClaudeConfiguration.allowedWorkingDirectories` before reaching argv, via the same `WorkingDirectoryAllowlist` helper Codex uses.
- No raw audio, screenshots, or secrets are part of any Claude event payload; message text is only ever the model's own visible output, not user secrets.

## Operational impact

- No new `Package.swift` dependencies beyond what Phase 10 already added to `AuraAgent` (`AuraShell`, `AuraPolicy`, `AuraTasks`).
- `Sources/AuraAgent/CodexProcessExecuting.swift` was removed (renamed/generalized to `AdapterProcessExecuting.swift`); `CodexAdapter.swift` and `Tests/AuraAgentTests/CodexTaskRunnerTests.swift` were updated to reference the renamed protocol — verified via a full `AuraAgentTests` re-run showing zero regression on the existing 46 Codex/Conversation tests before adding any new Claude code.
- Neither `ClaudeAdapter` nor `ClaudeTaskRunner` are wired into the `AURA` app composition root in this phase — matches existing precedent (Codex, VS Code, and Tasks adapters aren't wired in yet either).

## Migration

No breaking migration. `AuraConfiguration` gained a `claude: ClaudeConfiguration` field with full defaults; existing serialized configuration without a `claude` key decodes unchanged.

## Validation evidence

- `swift build --build-path /tmp/aurabuild-claude` (target-by-target: `AuraCore`, `AuraAgent`, `AuraAgentTests`) — all exit 0, zero warnings.
- `./scripts/aura-test.sh /tmp/aurabuild-claude AuraAgentTests` — 83/83 tests pass (46 pre-existing Codex/Conversation tests unmodified + 37 new Claude tests), run 3× consecutively with no flakiness observed.
- Authorized real invocation: `claude --permission-mode dontAsk --tools "" --setting-sources user --output-format stream-json --verbose --no-session-persistence -p "Follow the objective provided via standard input, then reply with exactly one word." <<< "Reply with exactly one word: ping"` — exit 0, 6 real JSONL lines captured as `Tests/AuraAgentTests/Fixtures/claude_smoke_success.jsonl`, exercised by `ClaudeEventNormalizerTests` and `ClaudeTaskRunnerTests` fixture-based tests. No tools were available (`--tools ""`), no files were touched, no network access beyond the single API call itself.

## Consequences

- **Positive:** AURA has a second real, policy-gated coding-agent adapter, proving the Phase 10 architecture (single-continuation adapter, `AdapterProcessExecuting` seam, upfront-policy-not-mid-run-prompt) generalizes cleanly to a CLI with materially different flag semantics and JSONL schema. Cost budgeting is more robust here than for Codex (CLI-native enforcement vs. advisory-only).
- **Negative:** No live file-write budget enforcement (structural tool-tier restriction only); item-level classification covers only `text` content blocks, `system` subtypes `hook_started`/`hook_response`/`init`, and `result`/`rate_limit_event` — `tool_use`/`tool_result`/`thinking`/`api_retry`/`plugin_install`/`stream_event` remain opaque pending an authorized run that actually exercises tools.
- **Risk:** `--bare`'s auth requirement means AURA cannot use Anthropic's own recommended hardening mode for API-key-only deployments without additional configuration surface (not built in this phase); `--setting-sources user` is a considered, documented substitute but is a narrower guarantee (still trusts the *operating user's* global config, where `--bare` trusts nothing at all).

# ADR-019 — Computer-Use Control Loop

- Status: Accepted
- Date: 2026-07-26
- Owners: Claude Sonnet 5 (Claude Code)
- Supersedes: —
- Superseded by: —

## Context

Phase 18 of the AURA implementation roadmap requires a bounded Observe → Plan → Policy → Act → Verify computer-use control loop, Accessibility text/ID anchoring preferred over coordinates, an emergency stop that disables all generated input, no-progress detection and escalation, and destructive-action default-deny with explicit confirmation — per `docs/subsystems/10_COMPUTER_USE.md`. Before this phase, AURA had the building blocks (`AuraAutomation`'s Accessibility observer/app controller from Phase 6, `AuraScreen`'s policy-gated, redacted window capture from Phase 17, `AuraPolicy`'s deny-by-default engine from Phase 5) but no subsystem that actually drives a bounded interaction loop against a live UI.

`ApplicationServices` (`AXUIElementPerformAction`, `AXUIElementSetAttributeValue`, `kAXModalAttribute`, and Accessibility tree traversal via `kAXChildrenAttribute`), `CoreGraphics` (`CGEvent` mouse/keyboard/scroll synthesis, `CGWarpMouseCursorPosition`), and `Carbon.HIToolbox` (named virtual-keycode constants, e.g. `kVK_Return`) are real Apple frameworks. Per this project's "no invented APIs" constraint, every API used in this phase's production code was verified with `swiftc -typecheck` probe compiles against the real installed SDK before being written, matching the Phase 17 (`ADR-018`) methodology — all probes compiled clean, including the `Carbon.HIToolbox` named keycode constants used in place of hardcoded hex values.

## Decision

1. **A new `AuraComputerUse` library target**, depending on `AuraCore`, `AuraPolicy`, `AuraAutomation`, `AuraScreen`, linking `AppKit`/`ApplicationServices`/`CoreGraphics` — following the established one-target-per-materially-new-subsystem precedent (`AuraPolicy` for Phase 5, `AuraAutomation` for Phase 6, `AuraScreen` for Phase 17). It composes over `AuraScreen.ScreenContextEngine` for Observe (reusing Phase 17's exclusion, policy-gating, and redaction guarantees rather than re-implementing capture) and `AuraPolicy.PolicyEngine` for Policy.

2. **A closed, typed `ComputerUsePlanning` protocol boundary is what makes "no raw model output becomes an executable action" true by construction**, not merely a convention. `ComputerUseControlLoop` never accepts or evaluates free text: a `ComputerUsePlanning` conformer must translate whatever a real planner (a model-backed adapter, deliberately out of scope for this phase — see Consequences) produces into a `ComputerUsePlan` of closed-enum `ComputerUseActionStep` values before the loop can act on them. A step's free-text `rationale` field is carried only for audit/logging and is never read by any decision path — proven by a dedicated test (`rationaleTextDoesNotAffectCapabilityDecision`) using an adversarial prompt-injection-shaped rationale string that has no effect on the step's evaluated capability.

3. **A step's semantic intent, not a coordinate or a raw action verb, drives its risk tier and capability.** `ComputerUseSemanticIntent` (`observe`/`navigate`/`toggleControl`/`fillField`/`submit`/`send`/`publish`/`purchase`/`delete`/`deploy`/`acceptLegalTerms`/`authenticateOrChangeCredential`) is a closed, non-extensible enum whose `riskTier` is a pure function, mirroring `Capability`'s own tiering. `Capability.forComputerUse(intent:)` maps each tier to one of four new capabilities (`computerUseObserve`/`computerUseInteract`/`computerUseMutate`/`computerUseDestructiveAct`), so every step is evaluated through the *existing* `PolicyEngine.evaluate` — no new authorization mechanism, following the Phase 17/18 precedent (ADR-018 decision 7, ADR-015) of a module performing its own real policy check rather than trusting an unenforced caller contract. Under `PolicyConfiguration`'s existing defaults (`denyByDefaultTiers = [.reversible, .mutation, .destructive]`), this alone makes every non-observation computer-use action denied by default with no grant — "destructive-action default-deny" falls out of composition with Phase 5's engine rather than a new mechanism.

4. **A fixed, non-configurable set of semantic intents can never execute on a bare `.allow` decision, even via a permissive grant.** The normative spec's "Never send, publish, purchase, delete, deploy, or accept legal terms without explicit confirmation" reads as an absolute rule alongside "Never interact with password fields" and "Never approve security dialogs automatically" — not something a `Grant`'s `confirmationRequirement` should be able to relax. `ComputerUseSemanticIntent.mandatoryConfirmationIntents` (send, publish, purchase, delete, deploy, acceptLegalTerms, authenticateOrChangeCredential) is a fixed `Set` constant, not a configuration field. `ComputerUseControlLoop` checks `step.semanticIntent.requiresMandatoryConfirmation` *after* receiving `.allow` from `PolicyEngine.evaluate` and unconditionally blocks execution if true, emitting `ComputerUseMandatoryConfirmationBlockedEvent` and returning `.mandatoryConfirmationBlocked` — proven by a test that issues an explicit `Grant` with `confirmationRequirement: .none` for `.computerUseDestructiveAct` and shows the step still never reaches the executor. This is the two-independent-off-switches pattern from ADR-018 decision 7, applied to confirmation instead of capture-enablement.

5. **Accessibility anchoring is preferred structurally, not merely by convention.** `UIAnchor` carries both an optional accessibility hint (role/title/identifier) and an optional normalized-coordinate fallback. `AXCGEventActionExecutor.execute` always attempts Accessibility resolution first when any hint is present (a bounded, 500-element-capped breadth-first traversal of the target application's AX tree via `kAXChildrenAttribute`, using `AXUIElementPerformAction`/`AXUIElementSetAttributeValue`); the coordinate fallback is used only when no hint was supplied or resolution fails. Every executed step's outcome (`UIActionExecutionResult.usedAccessibilityAnchor`) is carried into the audit event (`ComputerUseStepEvent`), so a caller can always tell whether a given step actually used the preferred path.

6. **Coordinate bounds are enforced at anchor construction, capped, and never silently clamped.** `UIAnchor.isValid`/`.coordinateFallbackInBounds` require any supplied coordinate fallback to be within `[0, 1]` on both axes (the same normalized, window-relative convention as `CaptureRegion`/`RecognizedTextRegion` from Phase 17) — an out-of-bounds coordinate is rejected outright as an `.invalidPlan` outcome, not clamped into range, matching ADR-018 decision 10's "approved... regions" precedent (an unapproved/invalid region is refused, not coerced).

7. **`.keyPress` supports a fixed set of named non-printable keys via real `Carbon.HIToolbox` constants, plus arbitrary Unicode text via `CGEvent.keyboardSetUnicodeString` — not a full virtual-keycode table.** Modified shortcuts (e.g. Cmd+A) are supported only for the fixed named-key set (return/tab/space/delete/escape/arrows); a modified single-character key press throws a typed error rather than guessing an ANSI keycode. This is a deliberate, honestly-scoped limitation (see Consequences) that avoids a large, error-prone hardcoded keycode table while still covering the realistic control-loop needs (submitting via Return, escaping dialogs, tabbing between fields, typing arbitrary text including non-ASCII).

8. **A single, channel-agnostic `EmergencyStopController` actor is the only kill switch**, and it never clears itself. `trigger(source: EmergencyStopSource, reason:)` accepts `.ui`/`.voice`/`.keyboard` identically — none is privileged or has different latency — satisfying "Emergency stop works from UI, voice, and keyboard" as a property of one shared mechanism rather than three independent implementations. `ComputerUseControlLoop` checks `emergencyStop.isActive` at the top of every iteration *and* before every individual step within a plan (a plan may contain several steps; a mid-plan trigger must not let queued steps finish first). Only an explicit `reset(actor:)` call re-arms input — the loop itself never resets it.

9. **No-progress detection compares the Phase-17 `ScreenObservation.contentHash` across consecutive iterations**, not a semantic diff — reusing an already-real, already-tested signal (SHA-256 of the captured image bytes) rather than inventing a second content-comparison mechanism. `noProgressIterationThreshold` consecutive unchanged observations (the first observation is always the "progressed" baseline, so the threshold is reached on the `(threshold + 1)`th observation) escalates to `.noProgress` rather than looping indefinitely.

10. **Identity change is checked at two independent points: the observed window/app, and each step's declared target.** `ComputerUseSessionTarget` binds a session to one approved `windowID`/`appBundleIdentifier` for its entire lifetime. Every iteration's `ScreenObservation.appBundleIdentifier` is compared against it (an app switch mid-task halts the loop with `.identityChanged`), and every individual step's `targetAppBundleIdentifier` is compared against it too (a step whose declared target drifted from the session's approved target halts the loop the same way) — a planner cannot redirect input to a different application by simply mislabeling one step.

11. **Unexpected-modal detection is a hard, always-checked halt, not a per-step confirmation.** `ModalDialogDetecting`/`AccessibilityModalDialogDetector` checks `kAXModalAttribute` on the frontmost application's focused window every iteration, plus a fixed always-unexpected bundle-identifier set (SecurityAgent, Keychain Access) regardless of modality flag — mirroring `ScreenContextConfiguration.sensitiveApplicationBundleIdentifiers`'s precedent of a hard, non-content-dependent exclusion list. A modal belonging to the session's own approved app is not reported (it may be part of the expected flow, e.g. an in-app confirmation sheet); a modal belonging to any other frontmost app, or a security surface, always halts the loop — directly implementing "Never approve security dialogs automatically" (the loop stops instead of risking an automatic dismissal) and "Stop on unexpected modal dialogs."

12. **Rate limiting throttles individual steps, not whole plans.** A step executed sooner than `minActionIntervalSeconds` after the previous one is blocked (`.rateLimited`) and skipped; the loop proceeds to the next step in the same plan rather than aborting it — a soft throttle against the approved target, distinct from the harder per-plan-aborting block reasons (secure-field focus, policy denial, execution failure).

13. **"Never interact with password fields" reuses Phase 17's `SecureFieldDetecting` protocol directly** rather than a second Accessibility-based detector — `AccessibilitySecureFieldDetector` is already real, already tested, and already the project's answer to "is a secure field focused in this application." Every step checks it immediately before Policy/Act; a focused secure field aborts the remaining steps in the current plan (not the whole session — the field may not be focused on the next iteration) with zero calls to the executor.

14. **Emergency stop is enforced at two independent layers, not one.** `ComputerUseControlLoop` checks `EmergencyStopController.isActive` before every iteration and before every individual step, but a re-verification pass found this alone made "disables all generated input" true only for callers that go through the loop — a hypothetical future caller invoking `AXCGEventActionExecutor` directly would bypass it entirely. `AXCGEventActionExecutor` now takes `EmergencyStopController` as a *required* (non-optional) constructor dependency and checks `isActive` unconditionally as the very first statement of `execute`, before even the permission-free `.wait` case — so the guarantee lives in the actual input-generation layer itself, not only in the orchestration layer that happens to call it first. This is the same "two independent off-switches" pattern as ADR-018 decision 7 (screen capture's `enabled` flag plus its own policy check), applied here to emergency stop instead of capture-enablement. Proven by a dedicated test (`executorItselfRefusesInputWhileEmergencyStopped`) that constructs the real executor directly (not through the control loop) and shows it refuses even a `.wait` action while stopped.

15. **`Task.isCancelled` is checked alongside, not instead of, the custom `EmergencyStopController`.** A re-verification pass found the loop had no path for a caller to stop it via Swift's standard structured-concurrency cancellation (`Task.cancel()`) — only the bespoke emergency-stop mechanism — unlike the established `MultiAgentOrchestrator` precedent (`docs/decisions/ADR-015`), which checks `Task.isCancelled` at multiple points in its own bounded loop. `ComputerUseControlLoop.run` now checks `Task.isCancelled` at the top of every iteration and before every individual step, returning `.failed(reason: "computer-use control loop cancelled", ...)` — giving "the loop is bounded and stoppable" a second, standard stop path in addition to the emergency-stop channel, consistent with how every other bounded loop in this codebase already behaves. Proven by a dedicated test (`taskCancellationMidPlanHaltsBeforeNextStep`) that cancels the loop's own enclosing `Task` mid-plan and confirms the remaining step never reaches the executor.

## Alternatives considered

- **A single `UIAnchor` enum case (`.accessibility` xor `.coordinate`)** instead of a struct carrying both. Rejected — the normative rule is "prefer... over," not "use exclusively one or the other"; a struct with an optional hint and an optional fallback lets one anchor express "try Accessibility, degrade to this coordinate if it fails," matching the actual preference semantics the spec asks for.
- **Trusting `PolicyEngine.evaluate`'s existing confirmation semantics alone for destructive computer-use actions**, with no additional control-loop-level check. Rejected — see decision 4; a `Grant` is user/operator-owned configuration data (ADR-006's own risk note: "grants are expected to originate from user action or trusted configuration," not guaranteed infallible), and the spec's "never... without explicit confirmation" phrasing for this specific action family reads as an absolute invariant the loop itself must guarantee, not a default that trusted configuration could override.
- **A full standard-US-ANSI virtual-keycode table for `.keyPress`** (covering every letter/digit with modifiers). Rejected — see decision 7; a ~40-entry hardcoded table is meaningfully more error-prone to get exactly right than the ~9-entry named-key table actually needed for realistic control-loop flows, and the Unicode-string typing path already covers arbitrary unmodified text, including non-ASCII.
- **Reading real element positions (`kAXPositionAttribute`/`kAXSizeAttribute`) to compute scroll targets from a resolved Accessibility element.** Rejected for this phase — scoped out to keep the executor's surface bounded; `.scroll` requires a coordinate fallback explicitly, a documented, honest limitation rather than a partially-implemented position-lookup path.
- **Letting the planner decide when to stop searching for progress (no engine-level no-progress detection).** Rejected — the acceptance gate requires the loop itself to be "bounded and stoppable" independent of planner behavior; a planner that keeps proposing plausible-looking but ineffective steps must not be able to keep the loop running past a fixed, engine-enforced ceiling.
- **Making `AXCGEventActionExecutor.emergencyStop` an optional parameter (defaulting to `nil`, i.e. "no check").** Rejected — see decision 14; an optional that defaults to skipping the safety check is exactly the kind of silently-omittable guarantee this project's "structural, not merely relying on caller discipline" philosophy exists to avoid. Making it required means every production construction site is forced to supply a real controller, and the compiler catches any future construction site that forgets.
- **Relying only on `EmergencyStopController` and treating `Task.isCancelled` as redundant/unnecessary.** Rejected — see decision 15; the two mechanisms serve different callers (an explicit user-facing stop action vs. Swift's standard structured-concurrency cancellation, e.g. a caller tearing down a `Task` group), and the existing `MultiAgentOrchestrator` precedent already establishes `Task.isCancelled` checking as this codebase's norm for any bounded loop — omitting it here would have been an unexplained inconsistency, not a deliberate simplification.
- **A single `PolicyEvaluationRequest` capability for all computer-use actions, gated only by target patterns.** Rejected — see decision 3; four distinct capabilities (one per risk tier) let an operator write tier-specific grants and deny rules using the *existing* `ResourcePattern`/`Grant`/`DenyRule` machinery with no new pattern-matching code.

## Security and privacy impact

- Every non-observation computer-use action is denied by default with no grant (`PolicyConfiguration.denyByDefaultTiers`'s existing default), and the six/seven named destructive-intent categories can never execute on a bare `.allow`, even via a misconfigured permissive grant.
- No raw model output is ever executed: the only boundary type `ComputerUseControlLoop` accepts is `ComputerUsePlan`, a closed, typed, non-string-eval'd structure; a step's free-text rationale is carried for audit only and never interpreted.
- Emergency stop is a single, channel-agnostic actor checked before every iteration and every individual step, and never self-resets.
- A focused secure text field (Phase 17's `SecureFieldDetecting`) blocks all step execution for that application, matching "never interact with password fields."
- An unexpected modal — including any window belonging to SecurityAgent/Keychain Access, or any modal window in a frontmost app other than the session's approved target — halts the loop rather than risking an automatic approval.
- Coordinates are always normalized `[0, 1]` and window-relative (never an independent display rectangle), and out-of-bounds coordinates are rejected outright, not clamped — consistent with Phase 17's region-scoping guarantees.
- Every phase transition (Observe/Plan/step-level Policy/Act/Verify), block reason, and terminal outcome emits a typed, redaction-safe audit event on the existing `AuraEventBus` — no raw screen pixels, typed text, or Accessibility element values in any payload.

## Operational impact

- `Sources/AuraCore/` gains `ComputerUseTypes.swift`, `ComputerUseEventPayloads.swift`, four new `Capability` statics plus `Capability.forComputerUse(intent:)` in `PolicyTypes.swift`, a new `ComputerUseConfiguration` nested inside `AuraConfiguration`, and additive fields on `ActorID` (`.computerUse`) and `AuraError` (`.computerUseError`).
- A new `AuraComputerUse` library target (depends on `AuraCore`, `AuraPolicy`, `AuraAutomation`, `AuraScreen`; links `AppKit`, `ApplicationServices`, `CoreGraphics`) and `AuraComputerUseTests` test target were added to `Package.swift`, following the `AuraScreen` precedent for macOS framework linking.
- Neither the `AURA` executable target nor `AURAIntegrationTests` were changed — `ComputerUseControlLoop` is not wired into the app composition root, matching the existing precedent for every subsystem since Phase 9.
- `scripts/aura-test.sh`'s default 8-bundle loop still omits `AuraPolicyTests`/`AuraTasksTests`/`AuraVSCodeTests`/`AuraMemoryTests`/`AuraContextTests`/`AuraScreenTests` (pre-existing gap) — `AuraComputerUseTests` joins that same explicitly-run-by-filter list.

## Migration

No breaking migration. No new database tables or schema migrations. Existing `AuraConfiguration` JSON files decode unchanged; a missing `computerUse` key merges in `ComputerUseConfiguration()`'s defaults exactly like every other nested configuration struct.

- The real `AXCGEventActionExecutor` and `AccessibilityModalDialogDetector` cannot exercise live Accessibility resolution or CGEvent delivery in this sandboxed CommandLineTools environment (no granted Accessibility permission); their safe-degradation paths are tested instead (a typed `AuraError`, never a crash or hang, when Accessibility is untrusted; `.wait` succeeding regardless of trust state) — matching the same "real API, deterministic-fake-tested, live-hardware-validation-deferred" pattern established by Phase 1's audio capture, Phase 2's wake-word detection, and Phase 17's screen capture.

## Consequences

- **Positive:** AURA has a real, bounded, stoppable computer-use control loop whose safety guarantees (destructive-action default-deny, mandatory confirmation for the named absolute-rule action categories, password-field non-interaction, unexpected-modal halting, coordinate bounds, and — after the re-verification pass documented above — emergency stop enforced at the executor layer itself plus standard `Task.isCancelled` cancellation) are structural — enforced by the loop's and executor's own code, not dependent on correct caller behavior or trusted grant configuration — directly satisfying the Phase 18 acceptance gate's four bullets.
- **Negative:** `.keyPress` only supports modifier combinations for a fixed set of ~9 named non-printable keys (Return/Tab/Space/Delete/Escape/arrows); a modified single-character shortcut (e.g. Cmd+A) throws a typed "unsupported" error rather than executing, an honest, documented scope limitation (decision 7) rather than a silently-wrong keycode guess. `.scroll` always requires a coordinate fallback (no Accessibility-element-position-based scrolling).
- **Risk:** `ComputerUseControlLoop` is not yet wired into any real caller (a live conversation turn, a model-backed `ComputerUsePlanning` conformer) — this phase proves the loop's own bounds, policy composition, emergency stop, no-progress detection, and destructive-action blocking are all correct in isolation with real (probe-verified) framework calls and deterministic fakes, but no subsystem yet actually drives a live computer-use session; a real planner backed by a model adapter (Codex/Claude/Copilot/Ollama, all already integrated in `AuraAgent` since Phases 10–13) is a named follow-up. Real-hardware validation (an actual granted Accessibility permission, real Accessibility tree traversal against live applications, real `CGEvent` delivery and receipt) is also necessarily deferred, matching every prior phase's identical limitation in this sandboxed environment.

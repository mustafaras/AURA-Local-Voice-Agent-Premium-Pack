# ADR-014 — Ollama Local Model Controller Architecture

- Status: Accepted
- Date: 2026-07-25
- Owners: Claude Sonnet 5 (Claude Code)
- Supersedes: —
- Superseded by: —

## Context

Phase 13 of the AURA implementation roadmap is the Ollama Local Model Adapter: "Implement Ollama model registry, capability routing, structured-output validation, model lifecycle, memory budget, health checks, and degraded mode" (`prompts/implementation/13_13_OLLAMA_ADAPTER.prompt.md`), gated on "Models are routed by capability, not name," "Structured output is validated before use," "Memory budget avoids simultaneous loading of large STT/vision/coding/TTS models," and "Degraded mode is safe and tested" (`docs/subsystems/20_OLLAMA_CONTROLLER.md`).

This phase is architecturally distinct from Phase 10–12 (Codex, Claude Code, GitHub Copilot): those adapters spawn a CLI subprocess and normalize a JSONL event stream. Ollama, once verified against a real, locally running `ollama serve` (version 0.32.3, installed at `/opt/homebrew/bin/ollama`, confirmed running via `GET http://127.0.0.1:11434/api/version`), exposes a local HTTP API well-suited to direct request/response calls — there is no CLI process to spawn for inference, no stdin/argv prompt-delivery problem, and no upfront tool-approval gate to negotiate. The `AdapterProcessExecuting`/`Command`/`ProcessRunner` machinery built for Phase 10–12 is therefore not reused here; a new `OllamaAPIClient` protocol plays the equivalent test-seam role.

Several facts discovered during implementation, all from real, local, harmless HTTP calls to the already-running daemon (no external network, no account/quota involved — this differs from Codex/Claude/Copilot, which required real, quota-consuming smoke tests against hosted services), materially shaped the design:

1. **`/api/tags` already reports per-model capabilities and size.** A real `GET /api/tags` call returned, for every installed model, a `capabilities` array (observed values: `completion`, `tools`, `thinking`, `vision`) and a `size` in bytes — directly satisfying "model registry with memory estimates [and] capabilities" without needing a second call.
2. **`/api/show` is real but not needed.** A real `POST /api/show` call for `gemma4:latest` returned a huge, verbose payload including `model_info`, whose field names are prefixed per model architecture (e.g. `gemma4.context_length`, `gemma4.attention.head_count`) — there is no architecture-independent way to read "context length" generically from this endpoint without guessing key prefixes per family, which would not be verifiable for models not yet observed. Since `/api/tags` already supplies every field this phase's registry needs, `/api/show` is not called anywhere in this implementation; its dynamic per-architecture keys are documented as a known, deliberately-unconsumed gap rather than fabricated.
3. **A model's local-vs-cloud status is not reliable to infer from its name.** Real `/api/tags` output showed `:cloud`-suffixed models (`minimax-m3:cloud`, `deepseek-v4-flash:cloud`, etc.) each carrying a `remote_host` field (e.g. `"remote_host":"https://ollama.com:443"`), while the genuinely local `gemma4:latest` entry had no `remote_host` field at all. `:cloud` is a naming convention Ollama's own tooling applies, not a contract this codebase can rely on — the authoritative, verified signal is the presence of `remote_host`. This directly matters for a "privacy-first, local... agent": routing a "privacy-sensitive reasoning" task to a `:cloud` model means the prompt is proxied to Ollama's hosted backend, which is exactly the kind of off-device action `docs/subsystems/20_OLLAMA_CONTROLLER.md`'s "local does not mean safe" warns about.
4. **`format` (a JSON Schema object) genuinely constrains `/api/generate` output.** A real request to the local `gemma4:latest` model with `format: {"type":"object","properties":{"classification":{"type":"string","enum":["urgent","normal"]}},"required":["classification"]}` returned exactly `{"classification":"urgent"}` for a request to classify an urgent-sounding message — confirming Ollama's structured-output support works end-to-end against a real local model, not just per official docs.
5. **`keep_alive` is the real idle-unload mechanism**, verified two ways: a request with `"keep_alive": 0` evicted the model immediately (`"done_reason":"unload"`, empty `response`, and the model disappeared from a subsequent `GET /api/ps`); a request with a positive `keep_alive` left the model resident with a real `expires_at` timestamp in `/api/ps`. Ollama's own daemon already implements idle unload — this phase delegates to it via `keep_alive` on every request rather than re-implementing a timer-based unloader in AURA.
6. **`/api/ps` reports real resident-memory usage** (`size`, `size_vram`, `expires_at`) — this is the live signal needed to enforce a memory budget across models AURA does not otherwise track, since Ollama itself does not cap total resident memory across simultaneously loaded models.
7. **A request for a nonexistent model returns HTTP 404 with `{"error":"model '...' not found"}`** — the real error envelope shape, used by every non-2xx response path in the client.
8. **`copilot`/`codex`/`claude`'s "upfront policy gate, no mid-run approval" pattern has no exact analog here**, since this phase does not execute tools, write files, or run shell commands at all — only text-in/text-out inference. The one real, policy-relevant boundary is local vs. cloud-proxied execution (fact 3 above), not read vs. write.

## Decision

1. **`OllamaAPIClient` protocol + `URLSessionOllamaAPIClient`**, mirroring the `AdapterProcessExecuting` test-seam pattern from Phase 10–12 but for HTTP instead of process spawning: `health()`, `listModels()`, `listRunningModels()`, `generate(model:prompt:format:keepAliveSeconds:)`, `unload(model:)`. Every response DTO (`OllamaTagsModel`, `OllamaPsModel`, `OllamaGenerateResponse`, `OllamaVersionResponse`, `OllamaErrorResponse`) decodes only fields verified in real responses; the daemon's output is consistently snake_case (unlike Claude's mixed-convention JSONL), so a single `.convertFromSnakeCase` `JSONDecoder` strategy is used throughout rather than per-field `CodingKeys`.
2. **`OllamaConfiguration.baseURL` is validated as loopback-only** (`127.0.0.1`, `::1`, or `localhost`) in `validate()` — AURA can never be pointed at a remote Ollama instance by configuration alone. `maxResidentModelBytes` defaults to 6 GB, deliberately conservative against the documented 16 GB unified-memory target profile, leaving headroom for STT/TTS/vision models running elsewhere in AURA. `allowCloudModels` defaults to `false`: cloud-proxied inference (fact 3) is opt-in, not a silent default.
3. **`OllamaModelRegistry`** caches `GET /api/tags` and exposes `route(capability:allowCloudModels:) -> OllamaRegisteredModel?`, a deterministic algorithm grounded entirely in real fields: eligible models must advertise raw capability `"completion"`; `.reasoning` additionally prefers (but does not require) `"thinking"`; cloud models (`remoteHost` present) are excluded unless `allowCloudModels` is true; among remaining candidates, the smallest `sizeBytes` wins, to minimize resident-memory pressure. Callers never name a model — satisfying the phase's "routed by capability, not name" acceptance criterion structurally.
4. **`OllamaFormatSchema`**, a narrow, purpose-built JSON Schema representation (not a general JSON-value type) covering exactly the two shapes this phase needs — `classification(labels:)` and `.summary` — both verified against the real local model in fact 4. `OllamaStructuredRequest.classify`/`.summarize` decode the response into a concrete typed struct and, for classification, independently re-validate the returned label is a member of the caller's requested set — defense-in-depth per AGENTS.md's "no raw model output may become an executable action," applied regardless of how well-behaved the one real observed case was.
5. **Two new capabilities**: `Capability.agentOllamaLocalInference` (`.reversible` — matches `PermissionRiskTier.reversible`'s "reversible local action") and `Capability.agentOllamaCloudInference` (`.destructive` — matches the tier's own documented definition, "external communication... or sensitive-data access"). `OllamaPolicyAdapter.request(model:capability:...)` selects between them based on the routed model's real `isLocal` flag (fact 3), never on its name. Local inference is allowed by default under the same `PolicyConfiguration` defaults Codex/Claude/Copilot tests use (`.reversible` in `allowByDefaultTiers`); cloud inference is denied by default and requires an explicit `Grant`, exercising the identical `PolicyEngine.evaluate`/`submitConfirmation` round-trip the other three adapters use — reusing `OllamaApprovalPresenting`, structurally identical to `CopilotApprovalPresenting`.
6. **Memory budget is actively enforced pre-load, not just observed post-hoc** — the one adapter in this phase's family that can act *before* a costly operation rather than only observing after, since `/api/ps` (fact 6) is queryable ahead of `/api/generate`. `OllamaAdapter.ensureMemoryBudget` sums resident `size_vram`, and if the routed model would not fit, evicts other resident models (oldest-`expires_at`-first, via `keep_alive: 0`, fact 5) until it does or degrades if it still would not fit even after evicting everything else.
7. **Thermal awareness uses `ProcessInfo.processInfo.thermalState`** (a real, already-available Foundation API — no invented mechanism), injected via a `thermalStateProvider` closure for testability. A `.critical` state refuses new model loads before routing/policy is even evaluated.
8. **Graceful degradation is a caller-supplied deterministic closure, not a bespoke rule engine.** Rather than inventing a generic "smart" fallback classifier inside this subsystem, `OllamaAdapter.classify`/`.summarize` accept an optional `deterministicFallback` closure invoked whenever health check, thermal state, routing, policy, or memory budget precludes real inference; without one, the call throws. `.reason` (open-ended reasoning) offers no fallback parameter at all — an honest scoping decision, since there is no safe deterministic substitute for free-form reasoning, matching AGENTS.md's "no placeholder... implementation" discipline. This reuses `AuraConfiguration`'s existing precedent for caller-owned deterministic rules (`ConversationConfiguration.deterministicStopCommands`) rather than building a second, competing mechanism.
9. **`OllamaTaskRunner: TaskRunner`** reads the target capability (and, for classification, a comma-separated label list) from `TaskRequest.context`'s existing free-form dictionary — identical mechanism to `CodexTaskRunner`/`ClaudeTaskRunner`/`CopilotTaskRunner`; no `AuraTasks` changes were needed.
10. **No `cancel(executionID:)` method exists on `OllamaAdapter`**, unlike the three CLI adapters. Each capability call is a single `async throws` request, not an `AsyncThrowingStream`; a caller cancels the enclosing `Task` and the in-flight `URLSession` request is interrupted the normal Swift-concurrency way. This is a genuine architectural difference, not an oversight — documented here rather than adding an unused method to match a pattern that does not apply.
11. **Multi-turn session continuation (`/api/generate`'s `context` array) is out of scope**, matching the `resume`-scoping precedent Codex/Claude/Copilot set for their own session-persistence features.

## Alternatives considered

- **Call `/api/show` for every registered model to enrich the registry with `model_info`.** Rejected — the dynamic, per-architecture key prefixes (fact 2) would require unverifiable guessing for any model family not already observed, and every field this phase's registry actually needs is already present in `/api/tags`.
- **Infer local-vs-cloud from the `:cloud` name suffix.** Rejected once `remote_host` was confirmed as the real, authoritative field (fact 3) — a naming convention is not a contract, and a future local model happening to be named with a `:cloud`-like suffix (or a cloud model without one) would silently misroute.
- **Build a generic JSON-value type (`AnyCodable`/`JSONValue`) to support arbitrary `format` schemas.** Rejected in favor of a narrow, purpose-built `OllamaFormatSchema` covering exactly the two shapes this phase needs — matches "don't introduce abstractions beyond what the task requires."
- **Implement a generic deterministic classifier for degraded mode** (e.g. keyword matching bundled into the adapter). Rejected — a bespoke rule engine embedded in this subsystem would either be too narrow to be broadly useful or dishonestly presented as more general than it is; letting the caller supply its own deterministic closure keeps the domain-specific rule where it belongs (with the caller who knows the task) while still satisfying "degrade to deterministic rules for simple commands."
- **Reuse `AdapterProcessExecuting`/spawn `ollama run <model>` as a subprocess instead of calling the HTTP API.** Rejected — the daemon's HTTP API is already running, is the mechanism `ollama`'s own CLI itself uses under the hood, and directly exposes `/api/ps`/`/api/tags`/structured `format` output that a subprocess-based text-in/text-out wrapper would have to re-derive or lose entirely.

## Security and privacy impact

- `OllamaConfiguration.baseURL` is structurally restricted to loopback hosts; no configuration value can point AURA's Ollama traffic at a non-local endpoint.
- Cloud-proxied inference (`.agentOllamaCloudInference`, `.destructive`) is denied by default and requires an explicit user `Grant`, exactly like the write-capable tiers of the Codex/Claude/Copilot adapters — a prompt only leaves the device with explicit authorization.
- Structured output is independently decoded and validated against the caller's requested schema/label set before being trusted, regardless of Ollama's own `format` constraint.
- No raw prompt or completion text appears in any audit event payload (`OllamaInferenceStartedEvent`/`OllamaInferenceCompletedEvent`/`OllamaStructuredValidationFailedEvent` carry only model names, capability names, timing, and error descriptions).
- All real HTTP calls made during implementation were local-only (`127.0.0.1:11434`), harmless (trivial classification/reasoning prompts), and consumed no external account quota — unlike the Codex/Claude/Copilot smoke tests, this phase's verification calls carry no cost or rate-limit exposure.

## Operational impact

- `AuraAgent` gains no new `Package.swift` dependency — `URLSession` is part of Foundation, already imported throughout the module.
- `OllamaAdapter`/`OllamaTaskRunner` are not wired into the `AURA` app composition root in this phase, matching existing precedent for the other three adapters.
- The default `maxResidentModelBytes` (6 GB) is a starting point, not a benchmarked value; `docs/subsystems/20_OLLAMA_CONTROLLER.md`'s own "benchmark actual target hardware" item remains open.

## Migration

No breaking migration. `AuraConfiguration` gained an `ollama: OllamaConfiguration` field with full defaults; existing serialized configuration without an `ollama` key decodes unchanged.

## Validation evidence

- Real, local, harmless HTTP calls against the running `ollama serve` (version 0.32.3): `GET /api/version`, `GET /api/tags` (13 models: 12 `:cloud`, 1 local `gemma4:latest`), `GET /api/ps` before/after load and after `keep_alive: 0` unload, `POST /api/generate` with a real JSON Schema `format` against `gemma4:latest` (returned `{"classification":"urgent"}`), `POST /api/generate` for a nonexistent model (404, `{"error":"model '...' not found"}`), `POST /api/show` for `gemma4:latest` (inspected, not used — see fact 2). All captured as `Tests/AuraAgentTests/Fixtures/ollama_{version,tags,ps,generate_structured,error_404}_real.json`.
- `swift build --build-path /tmp/aurabuild-ollama` (target-by-target and full) — exit 0, zero non-linker warnings.
- `./scripts/aura-test.sh /tmp/aurabuild-ollama AuraAgentTests` — 171/171 tests pass (130 pre-existing Codex/Claude/Copilot/Conversation tests unmodified + 41 new Ollama tests spanning fixture-based DTO decoding, registry routing rules, structured-request validation, adapter policy/health/thermal/budget/degraded-mode behavior, and full `AuraTaskEngine` integration), run 3× consecutively with no flakiness.
- One real test-design bug was found and fixed during verification: `OllamaTestFixtures.localModel()`'s default synthetic size initially mirrored the real `gemma4:latest` size (~9.6 GB), which exceeds `OllamaConfiguration`'s own conservative 6 GB default budget — causing two "happy path" tests to legitimately hit the (correctly-functioning) budget-exceeded path instead of exercising success. Fixed by lowering the fixture helper's default to 2 GB; tests that specifically exercise budget/eviction behavior already passed their own explicit `sizeBytes` and were unaffected.

## Consequences

- **Positive:** AURA gains a fourth model backend with the strongest privacy-relevant safety property of the four — a structural (not just conventional) local/cloud distinction enforced at the policy layer, plus the only pre-emptive (not merely observational) budget check among the four adapters, since resident-memory state is queryable before committing to an expensive operation.
- **Negative:** The registry never enriches entries with `/api/show`'s deeper `model_info` (context length for local models, exact parameter counts) — routing decisions use only `/api/tags`'s fields, which is sufficient for this phase's capability-routing and memory-budget needs but coarser than what `/api/show` could theoretically provide.
- **Risk:** `maxResidentModelBytes`'s 6 GB default is a reasoned starting point, not a hardware-benchmarked value; a future phase should validate it against real concurrent STT/TTS/vision model footprints on the documented 16 GB target device before this budget is relied upon in production.

## Context

Phase 19 of the AURA implementation roadmap requires completed threat models, prompt-injection/indirect-injection defenses, Keychain-backed secret handling with no hardcoded secrets, plugin manifest/signature/hash verification with sandboxing/quarantine/uninstall, network/path allowlists, an adversarial test suite, and independent review — per `prompts/implementation/19_19_SECURITY_HARDENING.prompt.md` and `prompts/implementation/AURA_PREMIUM_UNIFIED_MASTER.prompt.md` §Phase 19. Phases 0–18 already built substantial security infrastructure this phase composes over rather than duplicates: `PolicyEngine`'s deny-by-default capability/grant/confirmation engine (Phase 5), `Command`/`WorkingDirectoryAllowlist`'s path confinement (Phases 7/10/11), `OutputRedactor`/`RepositoryInstructionsScanner`'s secret pattern matching (Phases 7/12), `OllamaConfiguration`'s loopback-only network restriction (Phase 13), and `ContextRanking`'s memory-poisoning-resistant reference resolution (Phase 16). This phase's job is to fill the concrete gaps those phases left open: no Keychain integration existed anywhere in the codebase; no prompt-injection classifier existed; no plugin verification existed at all (Phase 23's full marketplace has no foundation to build on yet); secret-pattern lists were duplicated and out of sync between `OutputRedactor.default` and `RepositoryInstructionsScanner`; and `docs/security/30_THREAT_MODEL.md` was an empty worksheet template with no actual per-subsystem assessments.

`Security` framework (`SecItemAdd`/`SecItemCopyMatching`/`SecItemDelete` against `kSecClassGenericPassword`) and `CryptoKit.Curve25519.Signing` are real, stable Apple/Swift APIs. Per this project's "no invented APIs" constraint, both were verified with standalone probe programs before production code was written: a `swiftc -typecheck` probe confirmed the Keychain API shapes, then a compiled-and-run probe against the real Keychain in this development environment confirmed a live add/retrieve/delete round trip all returned `errSecSuccess` (2026-07-26) — not merely assumed from documentation. `Curve25519.Signing.PrivateKey`/`PublicKey` were similarly probe-verified (32-byte raw public key, 64-byte signature, `isValidSignature` round-trip) before `PluginVerifier` was written.

## Decision

1. **Two new library targets, `AuraSecurity` and `AuraPlugins`**, following the established one-target-per-materially-new-subsystem precedent. `AuraSecurity` (depends on `AuraCore`, `AuraPolicy`, `AuraStore`; links `Security`) holds the secret store, prompt-injection classifier, secret scanner, and network allowlist — independently usable value types/actors, not a single coordinating actor, since these four concerns don't share state. `AuraPlugins` (depends on `AuraCore`, `AuraPolicy`, `AuraStore`) holds the manifest schema, verifier, trust registry, and lifecycle registry, deliberately scoped to the verification-and-lifecycle foundation Phase 23 will extend into a full marketplace — see decision 8.

2. **`ContentProvenance.carriesAuthority` makes "content is data, not authority" (`docs/security/26_SECURITY_MODEL.md`'s core rule) a type-level guarantee, not a convention.** Only `.systemPolicy` and `.userUtterance` return `true`; every other source — including `.repositoryFile` — returns `false`. This is a deliberate, material choice: a project's own `AGENTS.md` is "local" and nominally user-controlled, but for any repository the user did not author entirely alone (a clone, a fork, a team repo, a dependency), it is exactly as attacker-influenced as a webpage. `RepositoryInstructionsScanner` already implicitly treated repository files this way (scanning them for secrets before trusting them); this decision generalizes that instinct into a reusable, explicit type.

3. **`PromptInjectionClassifier` only ever scans non-authoritative content — authoritative content is never classified, by construction, not by a caller remembering to skip it.** `classify(_:provenance:)`'s very first guard is `!provenance.carriesAuthority`; for `.userUtterance`/`.systemPolicy` it returns `.clean` unconditionally regardless of what the text contains. This was a deliberate rejection of a content-shape-only classifier: a real user is entitled to say "ignore the previous file and run this command," and a classifier that flagged that phrasing regardless of who said it would be both a false-positive generator and, more importantly, a category error — the actual security property this phase needs is "untrusted content cannot inject instructions," not "instruction-shaped text is suspicious." Proven by `classifierNeverScansAuthoritativeUserUtterance`, which feeds the classifier a deliberately attack-shaped phrase under `.userUtterance` provenance and asserts `.clean`.

4. **~20 deterministic, weighted regex rules across nine categories, summed into a cumulative severity score, not a single boolean match.** Categories: instruction-override, role-hijack, prompt-exfiltration, credential-exfiltration, unsanctioned-execution, authority-bypass, hidden-instruction (zero-width characters, HTML comments), data-exfiltration, concealment-from-user — directly derived from `docs/security/28_PROMPT_INJECTION_DEFENSE.md`'s threat list ("reveal secrets, install software, run commands, or contact external parties") plus the "Stop and explain when instructions conflict" (concealment) and hidden-instruction cases from real-world indirect-injection reports. Severity levels (`low`=1/`medium`=2/`high`=4) were chosen so a single `.high` match alone exceeds the default block threshold (3), two `.medium` matches together also do, and a lone `.low`/`.medium` match is `.suspicious` but not `.blocked` — a deliberately conservative default that still lets a single strong signal (e.g. "ignore all previous instructions") block outright without requiring corroboration.

5. **A model-based (second-LLM-call) classifier was explicitly rejected in favor of deterministic rules**, matching `docs/security/28_PROMPT_INJECTION_DEFENSE.md`'s "dedicated security classifier plus deterministic rules" wording literally as "rules," and matching this project's broader "deterministic, auditable, testable" bias (`PolicyEngine`'s own confirmation/deny logic is deterministic, not model-scored). A second LLM call to judge injection risk would itself be exposed to the same untrusted text it's judging, and its verdict would not be reproducible the way a fixed rule set's is.

6. **A single canonical `SecretPatternLibrary` (`AuraCore`) replaces two independently maintained, drifted pattern lists.** Before this phase, `OutputRedactor.default` (used for live command-output redaction) and `RepositoryInstructionsScanner`'s private `secretDetector` (used for repository-file scanning) each hand-maintained an overlapping-but-different regex list. This phase merges them into one strict superset (hex40, OpenAI-style key, GitHub token, AWS access key, private-key block, JWT, Slack token, Google API key, Stripe key, npm token) that both now reference, plus the new `SecretScanner` (`AuraSecurity`) for pre-flight scanning of prompts/ledger entries/events. A generic "key=value"-shaped heuristic was deliberately considered and rejected — `OutputRedactor.default` redacts real command output before logging, and a broad assignment heuristic would false-positive on ordinary diagnostic text, silently destroying legitimate output; only concrete, well-known secret *shapes* are listed.

7. **`KeychainSecretStore` uses `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`** — never iCloud-synced, never accessible before first unlock — the most restrictive `kSecAttrAccessible` value compatible with a background daemon needing access without requiring the user to be actively unlocked-and-present at every read. `SecretStoring` is a protocol (mirroring the `AdapterProcessExecuting`/`OllamaAPIClient` production-implementation-plus-test-seam pattern already established in Phases 10–13) so tests can substitute `InMemorySecretStore` without touching the real Keychain; `Tests/AuraSecurityTests/SecretStoreTests.swift` additionally exercises the *real* Keychain directly, per-test-unique service names, since this environment was confirmed (via probe) to have real Keychain access rather than requiring the "verified API, deterministic-fake-tested, live-hardware-deferred" fallback used for Accessibility/Screen Recording in Phases 1/2/17/18.

8. **`AuraPlugins` builds only the verification-and-lifecycle foundation this phase's acceptance gate actually requires ("Plugin verification enforced"), deliberately deferring marketplace-scale concerns to Phase 23.** `PluginRegistry` has no `execute` method anywhere — there is no plugin runtime, only verified, policy-gated bookkeeping a future runtime would consult. Explicitly out of scope for this phase, matching Phase 23's own listed deliverables: download/distribution, sandboxed XPC/helper execution, update/rollback flows, and any connection to an external vendor PKI or marketplace directory (`PluginTrustRegistry` is a local, operator-configured trust list only). This mirrors the precedent set by Phase 15 (Memory Engine) pre-seeding infrastructure Phase 21 (Advanced Memory Engine) later extends.

9. **Every plugin lifecycle transition is itself a `PolicyEngine.evaluate` call against a dedicated capability** (`Capability.pluginInstall`/`.pluginEnable`/`.pluginDisable`/`.pluginQuarantine`/`.pluginUninstall`), not a bespoke authorization check inside `PluginRegistry`. This follows the Phase 17/18/19 precedent of a module performing its own real policy check rather than trusting an unenforced caller contract (ADR-018 decision 7, ADR-019 decision 3). `pluginInstall` is `.destructive`-tier (introduces a new authority surface); `pluginQuarantine` is `.reversible`-tier despite sounding severe, because quarantining only ever *removes* authority — it is a protective action, never one that grants anything, so it does not warrant the same friction as installing new code.

10. **Quarantine is a deliberate one-way safety valve: there is no `unquarantine`.** `enable(pluginID:)` refuses a quarantined plugin unconditionally; recovery requires `uninstall` followed by a fresh, re-verified `install`. This was a deliberate rejection of a reversible quarantine — quarantine exists specifically for the case where a plugin's trustworthiness has become suspect, and allowing a simple re-enable would make the safety action too cheap to matter.

11. **`uninstall` retains the plugin's record and flips its state rather than deleting the row**, revoking every grant it was issued (best-effort per-grant revocation, since a grant already gone through another path is the same end state, not a failure). This directly implements "Uninstall removes runtime artifacts while preserving audit records" (Phase 23's stated acceptance gate) a phase early, at essentially no added cost, since `PluginRecord.state` already needed to be mutable for enable/disable/quarantine.

12. **`PluginManifest.signedPayload` is built from sorted, delimited fields, independent of upstream array/dictionary ordering**, so a vendor's signature is reproducible regardless of how `capabilities`/`supportedApplicationBundleIDs`/`networkDomains`/`executableDependencies` happen to be ordered when constructed. Proven by `signedPayloadIsDeterministicRegardlessOfArrayOrder`. `PluginVerifier.verify` checks structural validity → content-hash integrity → vendor trust → signature validity, in that fixed order, so a caller always learns the *first* real problem (e.g. a malformed manifest is reported as `.manifestInvalid`, never masked by a downstream `.signatureInvalid`).

13. **`NetworkAllowlist` is a general-purpose, deny-by-default primitive with no real caller yet — `OllamaConfiguration.allowedLoopbackHosts` (Phase 13) already governs the one real outbound network path in the codebase today, with a *stronger* guarantee.** A host-family restriction (loopback-only) is strictly stronger than a domain allowlist for Ollama's specific threat model (accidentally proxying prompt content to a remote host), so this phase did not retrofit `NetworkAllowlist` onto `URLSessionOllamaAPIClient` — that would have *weakened* the existing guarantee by replacing "must be loopback" with "must be on a configured list that could itself be misconfigured to include a non-loopback host." `NetworkAllowlist` exists for the next capability that legitimately needs non-loopback access (e.g. a plugin's declared `networkDomains`), which does not exist yet.

14. **`PathConfinement` (canonicalization-based path confinement, resolving `..` and symlinks before comparing) was built in `AuraCore` but deliberately not retrofitted into `Command.validate`/`WorkingDirectoryAllowlist`'s existing naive substring/prefix checks.** Those checks are already real, already tested, security-relevant code shipped and exercised across Phases 7/10/11; swapping their internals for canonicalized comparison risks behavior changes on macOS's symlink-heavy paths (`/tmp` → `/private/tmp`) that could silently break already-passing tests or, worse, already-correct production behavior, for a phase whose job is to *add* hardening, not risk regressing prior phases' shipped guarantees under time pressure. This is a documented, deliberate deferral — recorded as a residual risk in `docs/security/30_THREAT_MODEL.md` entry 5 — not an oversight; `PathConfinement` is real, complete, and available for the next module (or a dedicated future pass) to adopt.

15. **An independent security review (a fresh sub-agent with no prior context on how this phase's code was written, following the project's `security-review` skill methodology) was run against every new production file before this phase was considered complete**, and found one real, high-confidence issue: `PluginManifest.signedPayload` did not cover `requiredPermissions` (each `ResourcePattern`) or a capability's `riskTier` (only its `"domain.action"` identifier string) — both feed directly into the `Grant.patterns`/`Grant.capability` `PluginRegistry.install` issues from a verified manifest, so a manifest tampered with post-signing (e.g. widening `requiredPermissions` to `.any`, or re-declaring a capability at a lower risk tier under the same domain/action) would still pass Ed25519 signature verification. Fixed the same session, before any commit: `signedPayload` now encodes each capability's full `domain.action.riskTier` and each `requiredPermissions` entry via a new deterministic `ResourcePattern` encoding, with two new regression tests (`verifierRejectsManifestWithTamperedRequiredPermissions`, `verifierRejectsManifestWithMutatedCapabilityRiskTier`) proving both tamper paths now flip verification to `.signatureInvalid`. This is the same "re-verification finds and fixes real gaps before they ship" pattern already established by ADR-019 decisions 14–15 and the Phase 16/17 gaps recorded in `ledger/CURRENT_STATE.md`.

16. **`docs/security/30_THREAT_MODEL.md` was rewritten from an empty worksheet template into thirteen concrete, evidence-cited per-subsystem assessments** covering every externally-influenced input path across Phases 0–18 (audio, STT, screen/OCR, Accessibility/computer-use, shell output, VS Code bridge, agent adapter tool output, repository instruction files, memory/context, Ollama network, the new plugin manifests, configuration load, and the policy confirmation channel), each following the worksheet's eleven fields and citing real file:line evidence rather than describing a hypothetical design. One entry (configuration load) documents a genuinely open, currently-unmitigated residual risk (project-level configuration can weaken security-relevant defaults with no structural guardrail) rather than glossing over it — tracked explicitly for Phase 24, not silently omitted.

## Alternatives considered

- **Scanning all content, including `.userUtterance`/`.systemPolicy`, for injection-shaped patterns.** Rejected — see decision 3; this would flag legitimate user requests as attacks and misidentifies the actual threat (untrusted-content authority, not instruction-shaped phrasing).
- **A model-based prompt-injection classifier.** Rejected — see decision 5.
- **Keeping `OutputRedactor.default` and `RepositoryInstructionsScanner`'s pattern lists separate**, on the theory that command output and repository files have different threat profiles. Rejected — see decision 6; both lists were catching the same secret *shapes*, just inconsistently, and a real secret leaking through the narrower of the two lists was a genuine, avoidable gap, not a deliberate scoping choice.
- **A generic key=value secret-detection heuristic.** Rejected — see decision 6; false-positive risk on legitimate diagnostic output outweighs the marginal detection improvement over concrete known shapes.
- **Building `AuraPlugins` as part of Phase 23 instead of now, leaving Phase 19's "Plugin verification enforced" gate unmet until then.** Rejected — the acceptance gate is explicit and the master roadmap treats each phase's gate as blocking; a real, adversarially-tested verification foundation is buildable now without needing the marketplace/distribution/sandboxing pieces Phase 23 owns.
- **A reversible `unquarantine` operation.** Rejected — see decision 10.
- **Retrofitting `PathConfinement` into `Command.validate`/`WorkingDirectoryAllowlist` this phase.** Rejected — see decision 14; regression risk in already-shipped Phase 7/10/11 code outweighs the benefit of closing a documented, lower-severity residual risk this same phase.
- **Widening `NetworkAllowlist` to also govern Ollama's `baseURL`.** Rejected — see decision 13; would replace a stronger guarantee (loopback-only) with a weaker one (configurable domain list).
- **Raw `Security` framework `SecKey`/`SecKeyVerifySignature` C API for plugin signature verification**, instead of `CryptoKit.Curve25519.Signing`. Rejected — `CryptoKit` is already the project's hashing primitive (`PolicyEngine`'s own confirmation-challenge SHA-256), is type-safe, and is purpose-built for exactly this signature shape; the raw C API's `CFDictionary`-based key import adds surface area for a subtly wrong parameter with no corresponding benefit here.

## Security and privacy impact

- Untrusted content (repository files, memory retrieval, agent tool output, web content, screen OCR, terminal output, plugin manifests) can never be classified as carrying authority, regardless of its phrasing — a type-level guarantee, not a runtime check a caller could omit.
- Secrets are stored only in the macOS Keychain with the most restrictive practical accessibility attribute; no secret value ever appears in an event payload (`SecretAccessEvent` carries only the key and outcome).
- A single canonical secret-pattern list now backs command-output redaction, repository-file scanning, and pre-flight prompt/ledger/event scanning — no more silently-narrower coverage in any one of the three.
- Plugins cannot obtain authority without passing structural validation, content-hash integrity, vendor trust, and signature verification, in that order, and every capability they do obtain is a normal, revocable, policy-engine-tracked `Grant` — never ambient authority.
- Quarantine and uninstall are real, tested safety actions: a quarantined plugin cannot be re-enabled without a fresh install, and an uninstalled plugin's grants are actually revoked through `PolicyEngine`, not merely marked inactive in `AuraPlugins`' own bookkeeping.
- No hardcoded secrets were introduced by this phase (verified by manual review of every new file plus `SecretScanner` self-consistency with `OutputRedactor.default`).

## Operational impact

- Two new library targets (`AuraSecurity`, `AuraPlugins`) and two new test targets (`AuraSecurityTests`, `AuraPluginsTests`) added to `Package.swift`; `AuraSecurity` links the `Security` framework.
- `Sources/AuraCore/` gains `SecretPatternLibrary.swift`, `PathConfinement.swift`, `SecurityEventPayloads.swift`, `PluginEventPayloads.swift`, new `Capability` statics (`secretStore`/`secretRetrieve`/`secretDelete`/`pluginInstall`/`pluginEnable`/`pluginDisable`/`pluginQuarantine`/`pluginUninstall`), new `ActorID` cases (`.security`/`.plugin`), new `AuraError` cases (`.securityError`/`.pluginError`), and new `SecurityConfiguration`/`PluginConfiguration` structs nested inside `AuraConfiguration`.
- `Sources/AuraCore/RedactionEngine.swift` (`OutputRedactor.default`) and `Sources/AuraAgent/RepositoryInstructionsScanner.swift` (`secretDetector`) were refactored to source their pattern lists from the new canonical `SecretPatternLibrary` — a strict superset of both prior lists, so no existing detection behavior narrowed. Verified by re-running the full existing `AuraShellTests`/`AuraAgentTests` suites (including `redactorMasksDefaultPatterns` and every `RepositoryInstructionsScannerTests` case) after the refactor with no failures.
- Neither the `AURA` executable target nor `AURAIntegrationTests` were changed — matching the existing precedent for every subsystem since Phase 9, none of this phase's new code is wired into the app composition root yet.
- `scripts/aura-test.sh`'s default 8-bundle loop still omits `AuraPolicyTests`/`AuraTasksTests`/`AuraVSCodeTests`/`AuraMemoryTests`/`AuraContextTests`/`AuraScreenTests`/`AuraComputerUseTests` (pre-existing gap) — `AuraSecurityTests` and `AuraPluginsTests` join that same explicitly-run-by-filter list.

## Migration

No breaking migration. No new database tables or schema migrations — `PluginRegistry`'s persisted state reuses `AuraStore`'s existing generic `key_value_store` table via `setValue`/`value(forKey:)`, matching `PolicyEngine`'s own grant/deny-rule persistence convention. Existing `AuraConfiguration` JSON files decode unchanged; missing `security`/`plugins` keys merge in their defaults exactly like every other nested configuration struct (both default to fully deny-by-default: empty network allowlist, empty trusted-vendor-key map).

## Consequences

- Positive: a real, adversarially-tested prompt-injection defense and plugin-verification foundation now exist where none did before; secret handling has an actual Keychain-backed implementation instead of only a normative spec; three previously-divergent secret-pattern lists are now one.
- Positive: the threat model document went from an empty template to thirteen concrete, evidence-cited assessments, several of which honestly surface currently-open residual risks (configuration-layering weakening, unwired classifier integration, deferred path-confinement retrofit) rather than presenting a falsely complete picture.
- Limitation: `PromptInjectionClassifier` has no live caller yet on the screen-OCR, agent-tool-output, or memory-retrieval paths — it is complete and tested, but not yet integrated into those subsystems' real content flow, matching the same "not yet wired into a real caller" pattern already true of `ContextEngine`/`MemoryEngine`/`ScreenContextEngine`/`ComputerUseControlLoop` (Phases 15–18).
- Limitation: `KeychainSecretStore` has no live caller that evaluates `.secretStore`/`.secretRetrieve`/`.secretDelete` through `PolicyEngine` before calling it — the storage seam and its policy capabilities are built, but no real consumer (e.g. an agent adapter's API token) exists yet to exercise the end-to-end gated path.
- Limitation: `PluginRegistry` governs authority and lifecycle only — there is no real plugin execution runtime (no sandboxed XPC/helper process), matching Phase 23's explicit ownership of that piece.
- Limitation: `Command.validate`/`WorkingDirectoryAllowlist`'s pre-existing naive path-confinement checks were not hardened this phase — `PathConfinement` exists as the ready-to-adopt hardened primitive but the retrofit is deferred (decision 14).
- Limitation: configuration-layering cannot yet guarantee "higher-risk capabilities cannot be weakened by project config" — an honestly-documented open gap pending Phase 24.
- Next safe action: Phase 20 — Release Readiness, only on explicit user go-ahead. The independent security review required by this phase's acceptance gate ("Independent review completed and findings addressed or accepted") is complete — its one finding was fixed, not merely accepted, before this phase's ledger entry.

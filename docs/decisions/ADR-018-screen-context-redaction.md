# ADR-018 — Screen Context and Redaction

- Status: Accepted
- Date: 2026-07-26
- Owners: Claude Sonnet 5 (Claude Code)
- Supersedes: —
- Superseded by: —

## Context

Phase 17 of the AURA implementation roadmap requires ScreenCaptureKit-based approved-window capture, a redaction pipeline (secure text fields, password managers, authentication codes, financial data, private notifications, user-defined regions, pattern-matched secrets), sensitive-app/assistant-self exclusions, freshness metadata, and zero-retention defaults — per `docs/subsystems/12_SCREEN_CONTEXT.md`. Before this phase, AURA had no screen-observation subsystem at all; `Capability.screenCapture`/`.screenReadText` existed in `PolicyTypes.swift` (both `.observation` tier) since an earlier phase but were never referenced by any real code path.

`ScreenCaptureKit`, `Vision`, and `ApplicationServices` are real Apple frameworks with genuine Objective-C-header-defined APIs (most of `ScreenCaptureKit`'s Swift surface is bridged from headers, not a native `.swiftinterface` — only its newer `SCContentSharingPicker` extension is a native Swift overlay). Per this project's "no invented APIs" constraint, every API used in this phase's production code was verified two ways before being written: (1) reading the real header files under `MacOSX.sdk/System/Library/Frameworks/ScreenCaptureKit.framework` and `ApplicationServices.framework`, and (2) compiling small standalone probe snippets with `swiftc -typecheck` against the real SDK to confirm exact Swift-bridged names (e.g. `SCWindow.isOnScreen`, not `.onScreen` — the obvious guess is a compiler error, since Swift 3 renamed the ObjC `onScreen` getter).

## Decision

1. **A one-shot screenshot API (`SCScreenshotManager.captureImage(contentFilter:configuration:)`), not a continuous `SCStream`.** The normative spec's capture policy is "off until granted and actively needed" with per-observation "capture time" freshness metadata — discrete point-in-time observations, not a video feed. A live `SCStream` would itself contradict "actively needed" by running continuously regardless of whether anything asked for a fresh observation. `SCScreenshotManager.captureImage` (stable since macOS 14.0, well within this project's macOS 27+ target) captures exactly one frame on demand and returns a `CGImage` directly — no `SCStream`/`SCStreamOutput`/live delegate/`CMSampleBuffer` handling is needed anywhere in this phase.

2. **A single `ScreenWindowSource` protocol covers both enumeration and capture**, rather than two independent protocols. Real `SCWindow` instances have no public initializer (`- (instancetype)init NS_UNAVAILABLE`) — they can only come from `SCShareableContent`. Capturing a specific window therefore requires reusing the exact `SCWindow` object that answered the enumeration call, which the production adapter (`ScreenCaptureKitWindowSource`) does via an internal `[Int: SCWindow]` cache populated by `listCapturableWindows()` and consumed by `captureImage(windowID:maxDimension:)`. Splitting these into two protocols would force that cache to be shared awkwardly across two independently-testable types for no real benefit — the public API surface everywhere else in `AuraScreen` only ever needs the plain, constructible `ScreenWindowDescriptor`.

3. **Sensitive-app and password-manager/notification exclusion is a hard pre-capture block, not a post-capture redaction.** `ScreenContextEngine.isApproved` filters both `listApprovedWindows()`'s output and `captureWindow`'s target *before* any screenshot is ever taken, using `ScreenContextConfiguration.sensitiveApplicationBundleIdentifiers` (seeded with known password managers, Notification Center, and Keychain/SecurityAgent) plus the assistant's own bundle identifier. This is a strictly stronger guarantee than "capture, then redact the parts that look sensitive" — an OCR/pattern-match pass can miss something; never taking the screenshot cannot. Consequently, `RedactionCategory` has no `.passwordManagerApplication`/`.privateNotificationApplication` cases — they would never be constructed by any real code path, since those apps' windows never reach the redaction pipeline at all.

4. **Secure-field focus masks the entire captured frame, not just the field's own bounding box.** `AccessibilitySecureFieldDetector` (real `AXUIElementCopyAttributeValue` calls, `kAXFocusedUIElementAttribute` → `kAXSubroleAttribute` compared against `kAXSecureTextFieldSubrole`, mirroring the existing, already-tested `AuraAutomation.AccessibilityObserver` pattern) reports only a yes/no "is a secure field focused in this app," not a bounding box. `RedactionPipeline.redactions` treats a true answer as reason to mask the whole frame (`RedactionMatch` at `(0, 0, 1, 1)`) and skip every other check for that capture — a conservative choice given no reliable sub-region is available, matching this project's "never resolve/act on weak evidence" posture from Phase 16.

5. **Financial-data and authentication-code detection are structurally separate from the user-configurable `redactionPatterns` list.** The spec lists "authentication codes," "financial data," and "secrets matching configured patterns" as three distinct bullets. `RedactionPipeline` therefore runs two fixed, non-configurable regex checks (13-19 digit runs for financial data; labeled 4-8 digit codes for authentication codes) *in addition to* whatever `ScreenContextConfiguration.redactionPatterns` a deployment configures, categorizing generic pattern hits as `.patternMatchedSecret`. This guarantees the two named-in-spec categories are always detected even if an operator's custom pattern list is edited or emptied, while `redactionPatterns` remains the deployment-tunable catch-all the spec's "configured patterns" bullet actually describes.

6. **OCR (`Vision`) is the only real way to redact based on captured *content*, but is fully abstracted behind `TextRecognizing`.** Pixels cannot be regex-matched; text must be extracted first. The production `VisionTextRecognizer` uses real `VNRecognizeTextRequest`/`VNImageRequestHandler` calls (verified via probe-compile). Every other piece of `AuraScreen`'s logic — exclusion, policy gating, the redaction pipeline itself, retention — depends only on the `TextRecognizing` protocol, so "redaction correctness verified with adversarial fixtures" is a real, deterministic unit-test property (scripted `RecognizedTextRegion`s) independent of whether live OCR is available or how any particular macOS version's Vision model behaves.

7. **Screen capture has two independent off-switches, not one.** `ScreenContextConfiguration.enabled` (default `false`) is checked first and unconditionally blocks capture with zero calls to any real API — the literal "off until granted" switch. Independently, every capture request that passes the master switch and exclusion checks is still run through a real `PolicyEngine.evaluate(_:)` call for `Capability.screenCapture` (`.observation` tier). Under `PolicyConfiguration`'s defaults, `.observation` tier is not in `denyByDefaultTiers` and does not trigger default confirmation, so it evaluates to `.allow` with no matching grant — meaning `PolicyEngine.evaluate` alone would not enforce "off by default." The two checks are deliberately complementary: `enabled` is the primary, unconditional kill switch (matching `AudioConfiguration`'s/`WakeWordConfiguration`'s privacy-opt-in precedent), while the policy check is what makes every capture attempt auditable via the existing `PolicyEvaluationRequestedEvent`/`PolicyDecisionEvent` mechanism and lets an operator add a scoped `DenyRule` (e.g. targeting one additional sensitive app) without a code change.
   This module therefore depends on `AuraPolicy` directly and calls `evaluate` itself, following the Phase 14 (`WorktreeManager`/`MultiAgentOrchestrator`) precedent of a self-contained module performing its own real policy check — not the older `AuraShell`/`AuraVSCode`/`AuraTaskEngine` precedent of leaving gating entirely to an as-yet-unbuilt caller (already flagged in `ledger/CURRENT_STATE.md` as an unresolved gap for those modules).

8. **Zero-retention is structural, not a flag that is merely checked.** `captureWindow`'s local `image: CGImage` is never stored anywhere unless `configuration.retainRawFrames == true`; under the default `false`, the value simply falls out of scope at the end of the method and is deallocated by ARC — there is no code path that could accidentally retain it. When explicitly opted in, retention reuses the *existing* `PrivacyConfiguration.screenshotRetentionDays` (present since Phase 0, previously unused) rather than introducing a duplicate field, and `ScreenContextEngine` enforces both a count cap (20 frames) and real age-based expiry (`purgeExpiredRawFrames`, run automatically on every retain and separately exposed for deterministic testing) — mirroring `MemoryEngine.enforceRetention`'s pattern of a real, callable retention sweep rather than a documented-but-unenforced intention.

9. **Window titles are redacted through the same `configuration.redactionPatterns` list, via the existing `OutputRedactor`** (Phase 7), not a new title-specific redaction mechanism — a window title can itself leak content (e.g. a bank statement's filename), and reusing the already-real, already-tested regex redactor is simpler and more consistent than inventing a second text-redaction code path alongside `RedactionPipeline`'s OCR-region logic.

10. **Region scoping is always a sub-rectangle of an already-approved window, never an independent screen rectangle.** The mission text asks for "window/region scoping" and the acceptance gate for "only approved windows/**regions** captured" — an initial implementation pass covered only window scoping, caught on re-review against the pasted deliverable/acceptance-gate text and completed before this ADR was finalized. `ScreenContextEngine.captureWindow(windowID:region:)` accepts an optional `CaptureRegion` (window-relative, normalized `[0, 1]`, the same convention already used by `RecognizedTextRegion`/`RedactionMatch`/`UserDefinedRedactionRegion`). Regions are deliberately scoped *within* a window that has already passed sensitive-app/self-exclusion and policy checks, rather than as an independent display rectangle — an unscoped display region could straddle a sensitive application's window that was never itself approved, silently reintroducing exactly the bypass decision 3 exists to prevent. `CaptureRegion.isValid` (positive size, fully within `[0, 1]`) is checked before any capture is attempted; an invalid region is a new, distinct block reason (`.invalidRegion`), not silently clamped — "approved... regions" means a region can fail approval too, not only a window. `ScreenCaptureKitWindowSource.absoluteSourceRect` translates the window-relative region into the display-space `CGRect` `SCStreamConfiguration.sourceRect` actually requires (per `SCStream.h`: "specified in points in the display's logical coordinate system," *not* window-relative) by adding the region's fraction of the window's own frame origin/size — a real, header-verified conversion, tested as a pure function independent of live capture. Because `Vision`'s recognized-text bounding boxes are already relative to whatever image it was handed (the cropped region, when one was requested), only `configuration.userDefinedRedactionRegions` — defined once, window-relative, independent of any particular capture — need translating per capture; `ScreenContextEngine.regionsRelativeToCapture` clips each configured region to the requested `CaptureRegion` and re-expresses the surviving overlap relative to it, dropping regions with no overlap at all rather than reporting a masked area that isn't actually in the captured image.

## Alternatives considered

- **A continuous `SCStream` with an `SCStreamOutput` delegate.** Rejected — see decision 1; contradicts "off until actively needed" and adds significant unneeded complexity (frame-rate configuration, delegate lifecycle, `CMSampleBuffer`→`CGImage` conversion) for a spec that only asks for discrete, on-demand observations.
- **Two separate protocols for window enumeration and image capture.** Rejected — see decision 2; `SCWindow`'s lack of a public initializer makes a single shared-cache abstraction the only clean way to keep both operations independently fake-able in tests.
- **Redact only within the specific secure field's bounding box, estimated from window geometry.** Rejected — Accessibility gives a reliable yes/no for "is a secure field focused," not a trustworthy sub-region; masking the whole frame is the conservative, honestly-scoped choice given the information actually available.
- **Treat password managers/notifications as redaction-pipeline categories (mask the relevant region within an otherwise-captured window).** Rejected — see decision 3; a hard pre-capture exclusion is strictly safer and was already the natural design once `sensitiveApplicationBundleIdentifiers` existed for exclusion purposes.
- **Rely solely on `PolicyEngine.evaluate`'s default tier matrix for "off until granted."** Rejected — `.observation`-tier capabilities evaluate to `.allow` by default with no grant (see decision 7); a dedicated `enabled` flag is the only mechanism that actually starts capture in the "off" state the spec requires.
- **Add a new `ScreenContextConfiguration.rawFrameRetentionDays` field.** Rejected — `PrivacyConfiguration.screenshotRetentionDays` already exists for exactly this purpose (present since the Phase 0 bootstrap, previously unused); duplicating it would create two sources of truth for the same setting.
- **An independent, window-agnostic screen-rectangle capture (region scoping with no owning window at all).** Rejected — see decision 10; would let a caller capture an arbitrary display rectangle that happens to overlap a sensitive application's window, bypassing the exclusion checks that only run against a specific target window's descriptor.
- **Silently clamp an out-of-bounds region to `[0, 1]` instead of rejecting it.** Rejected — the acceptance gate says "approved windows/regions," implying an unapproved region is refused, not silently coerced into something the caller didn't actually ask for; a new `.invalidRegion` block reason makes this an explicit, auditable outcome instead.

## Security and privacy impact

- Screen capture is off by default (`ScreenContextConfiguration.enabled == false`) and every attempted capture is policy-audited regardless of the master switch's state (the `ScreenCaptureRequestedEvent` fires before the `enabled` check).
- Sensitive applications (password managers, Notification Center, Keychain/SecurityAgent) and the assistant's own window are excluded from both window listing and capture before any screenshot is taken — never merely redacted after the fact.
- A focused secure text field masks the entire captured frame, not just the field itself.
- Financial-data and authentication-code detection cannot be disabled by editing the configurable pattern list — they are independent, always-active checks.
- No raw captured image is retained anywhere by default; the opted-in retention path is bounded by both count and a real, enforced age-based expiry reusing the existing `PrivacyConfiguration.screenshotRetentionDays`.
- `RedactionMatch` never carries the matched sensitive text itself, only a category and a non-sensitive pattern description (e.g. "financialData-shaped text") — verified by an explicit test (`redactionMatchNeverCarriesTheMatchedSensitiveText`).
- Every capture attempt, block, and observation emits a typed, internal-sensitivity audit event on the existing `AuraEventBus` — no new logging channel, no raw pixels or unredacted text in any event payload.

## Operational impact

- `Sources/AuraCore/` gains `ScreenContextTypes.swift`, `ScreenContextEventPayloads.swift`, plus additive fields on `ActorID` (`.screen`) and `AuraError` (`.screenCaptureError`), plus a new `ScreenContextConfiguration` nested inside `AuraConfiguration`.
- A new `AuraScreen` library target (depends on `AuraCore`, `AuraPolicy`; links `AppKit`, `ApplicationServices`, `ScreenCaptureKit`, `Vision`) and `AuraScreenTests` test target were added to `Package.swift`, following the `AuraAutomation` precedent for macOS framework linking.
- Neither the `AURA` executable target nor `AURAIntegrationTests` were changed — `ScreenContextEngine` is not wired into the app composition root, matching the existing precedent for every subsystem since Phase 9.
- `scripts/aura-test.sh`'s default 8-bundle loop still omits `AuraPolicyTests`/`AuraTasksTests`/`AuraVSCodeTests`/`AuraMemoryTests`/`AuraContextTests` (pre-existing gap) — `AuraScreenTests` joins that same explicitly-run-by-filter list.

## Migration

No breaking migration. No new database tables or schema migrations. Existing `AuraConfiguration` JSON files decode unchanged; a missing `screen` key merges in `ScreenContextConfiguration()`'s defaults (capture disabled) exactly like every other nested configuration struct.

## Consequences

- **Positive:** AURA has a real, tested screen-context subsystem whose exclusion and redaction guarantees are structural (never-captured, never-retained) rather than best-effort filters applied after the fact, directly satisfying the Phase 17 acceptance gate's "only approved windows/regions captured" and "no retained screen data unless diagnostic opt-in" — including region-level approval (an invalid region is refused, not silently clamped) once the initial window-only gap was caught and closed.
- **Negative:** OCR-based redaction depends on `Vision`'s text recognition accuracy for real captures — a financial number or code rendered as an image (not selectable/recognizable text, e.g. a stylized logo containing digits) would not be caught by the OCR-dependent categories, though the built-in secure-field and sensitive-app exclusions are unaffected since they never depend on recognized text at all. This is an honest limitation of OCR-based detection, not a bug.
- **Risk:** `ScreenContextEngine` is not yet wired into any real caller (a live conversation turn, the computer-use control loop planned for Phase 18) — this phase proves window exclusion, policy gating, redaction, and retention are all correct in isolation with real (probe-verified) framework calls, but no subsystem yet actually requests a capture during live operation. Real-hardware validation (actual Screen Recording permission grant, real window content, real Vision OCR accuracy on live screenshots) is also necessarily deferred — this sandboxed CommandLineTools environment has neither a granted permission nor, likely, a real display to capture from, matching the same "real API, deterministic-fake-tested, live-hardware-validation-deferred" pattern already established for Phase 1's audio capture and Phase 2's wake-word detection.

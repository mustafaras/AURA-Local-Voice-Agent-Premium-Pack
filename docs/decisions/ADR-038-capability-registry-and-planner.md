# ADR-038 - Capability Registry and Typed Planner

- Status: Accepted
- Date: 2026-08-04
- Owners: Claude Code
- Supersedes: The `ToolRegistry`/`ToolContract` closed five-`IntentKind` switch introduced in R1/R2.
- Superseded by: -

## Context

R1/R2 routed every user-reachable action through `ToolRouter.route(_:)`'s `switch intent.kind`, backed by `ToolRegistry.defaultRegistry()` — a fixed dictionary keyed by `IntentKind`, a closed `CaseIterable` enum. Adding a new capability required widening both the enum and the switch, and nothing prevented a caller (including a future model-proposed plan) from inventing a capability or a risk tier the registry never reviewed. `RISK-CLOSED-TOOL-ROUTER` documents exactly this: "Five-intent switch prevents safe extensibility and encourages disconnected features."

R3's mission (`04_R3_CAPABILITY_REGISTRY_AND_PLANNER.prompt.md`) is to replace this with a versioned, namespaced capability manifest registry and a bounded typed planner, so R4-R8 can add capabilities without touching core routing architecture.

This work started with two of R2's three completion blockers still open by explicit user instruction (`RISK-STT-MIC-NOT-CAPTURING` needs the user physically present; `RISK-STRUCTURED-NLU-MODEL-QUALITY`'s residual sampling variance is an accepted bounded risk) — the user directed proceeding to R3 rather than closing R2 first. This is recorded here and in the program ledger as a deliberate, explicit deviation from the prompt manifest's normal dependency order, not an oversight.

## Decision

1. `CapabilityManifest` (`Sources/AuraIntent/CapabilityRegistry.swift`) is the versioned contract for one capability: stable `id`/`version`, localized `CapabilityPresentation` (title/description/examples per `DialogueLanguage`, never leaking internal terminology to the user), input/output schema descriptions, owning adapter, `requiredCapability: Capability` (risk tier lives here, on the existing `AuraCore` type — never duplicated or re-derived elsewhere), side effects, required grants/network domains/external dependencies, locality (local/cloud), idempotency, `CapabilityExecutionBudget` (timeout, cancellation, retry, concurrency), confirmation rule, verification method, rollback strategy, sensitivity, retention behavior, and per-stage minimum evidence class.
2. `CapabilityRegistry` (actor) is the sole production source of capability contracts. Every lookup (`manifest(id:version:)`, `resolveLatest(id:)`) returns `nil` for anything unregistered or version-mismatched — unknown IDs and schema versions fail closed, never fall back to a guess. `CapabilityAvailability` (`.ready` / `.degraded(reason:)` / `.disabled(reason:)`) is tracked per qualified ID separately from the manifest itself, so a capability's schema/risk can be reviewed and registered before its adapter exists, and truthfully marked not-yet-reachable rather than falsely presented as ready.
3. `CapabilityPlanner` (actor, `Sources/AuraIntent/CapabilityPlanner.swift`) validates and builds `Plan`s against the registry — never against caller-supplied metadata. `validateStep` rejects an unknown capability ID, a disabled/degraded capability, or a missing/empty required argument, and always recomputes `riskTier`/`requiredCapability` from the registry's manifest, so a caller (including a future model-proposed step) can never lower or invent risk. `buildPlan` rejects plans exceeding `maxStepsPerPlan`, self/forward dependency references (cycles), and out-of-range dependency indices. `PlanResult` is the bounded outcome set the mission specifies: `.directAnswer`, `.clarification`, `.singleCapabilityCall`, `.multiStepPlan`, `.delegatedTask`, `.refusal`. Every `Plan` carries a `SHA256` `fingerprint` over its steps' capability ID/version/arguments/dependencies — content-derived and stable across replans of identical steps, but different whenever any step's content differs — this is the confirmation-binding and immutability identity the mission requires ("plans must be immutable after confirmation; replanning creates a new plan identity"), mirroring `PolicyPlanHasher`'s existing fingerprint discipline.
4. `ToolRouter` (`Sources/AuraIntent/ToolRouter.swift`) now sources its contract for every `IntentKind` from `CapabilityRegistry` via `resolveContract(for:)`, which requires `.ready` availability — the prior `ToolRegistry`/`ToolContract` types are deleted, not left as parallel dead code. `IntentKind → capability ID` is a single, isolated mapping function (`capabilityID(for:)`); the five existing handler methods (`handleConverse`, `handleAppLifecycle`, `handleShellExecute`, `handleCodingAgentRun`) are otherwise unchanged, so their already-tested execution/verification/policy-resolution behavior is preserved exactly.
5. `InitialCapabilitySet` (`Sources/AuraIntent/InitialCapabilitySet.swift`) registers the mission's target capability set. Ten are `.ready`: the five pre-existing NLU-reachable capabilities (`aura.converse`, `app.activate`, `app.quit`, `shell.execute_typed`, `agent.coding_run`) plus four newly reachable through direct `AuraKernel` methods rather than the bilingual classifier (`app.discover`, `app.hide`, `task.status`, `task.cancel` — each backed by an already-real, already-tested `AuraAutomation`/`AuraTaskEngine` method) plus `capability.health` (backed by the registry's own snapshot). Four (`filesystem.open_file`, `filesystem.open_folder`, `filesystem.reveal`, `url.open`) are registered `.disabled` with a truthful, specific reason — their manifests are real and reviewed, but no adapter is wired yet. This is the mission's explicitly sanctioned "disconnected future capabilities are visibly disabled rather than falsely ready," applied honestly rather than skipped.
6. `AuraKernel` gained a `capabilityRegistry` property (constructed and populated via `InitialCapabilitySet.registerAll` during `construct()`, recorded in `RuntimeHealthRegistry`) and five new direct methods (`discoverApplications`, `hideApplication`, `taskStatus`, `taskCancel`, `capabilityHealthSnapshot`), each policy-gated through the exact same `PolicyEngine.evaluate` every `ToolRouter`-routed capability uses (`evaluateDirectCapability`), fail-closed on `.confirm` since no confirmation presenter is wired for this direct-call path yet.
7. New `Capability` statics were added to `PolicyTypes.swift` (`taskStatus`, `appDiscover`, `appHide`, `fileOpen`, `fileReveal`, `urlOpen`, `capabilityHealthQuery`) — purely additive to the existing namespaced `domain.action` extension, no existing capability changed.

## Alternatives considered

- Widen `IntentKind` and `ToolRegistry`'s dictionary for every new capability. Rejected — this is exactly the closed-switch problem R3 exists to fix; it does not scale to R4-R8's adapters without repeatedly touching core routing.
- Give every one of the 12 target capabilities NLU/classifier reachability in this pass. Rejected for this pass on scope/time grounds: the bilingual rule-based classifier's Turkish morphology/golden-corpus discipline (R2) is itself a multi-day effort per intent family; four capabilities were instead given a real, tested, non-NLU reachability path (direct `AuraKernel` methods, the same pattern `runtimeHealthSnapshot()` already uses) rather than left disconnected, and the remaining four (filesystem/url, which also need genuinely new adapter code, not just classifier patterns) are truthfully registered `.disabled` rather than half-implemented or silently claimed complete.
- Silently keep `ToolRegistry`/`ToolContract` alongside the new registry "just in case." Rejected — leaving a second, unused production-shaped source of capability contracts around directly contradicts the completion gate's "the registry is the sole production source for user-reachable tools" and invites drift; it was deleted, with the one dependent test assertion migrated to the new manifest.
- Derive a step's risk tier from caller-supplied metadata for performance. Rejected — `CapabilityPlanner.validateStep` always re-resolves the manifest and takes `riskTier`/`requiredCapability` from it, never from the request, matching `ToolRouter.resolvePolicy`'s existing "policy is authoritative" discipline and directly satisfying "configuration cannot lower security."

## Security and privacy impact

Unknown or out-of-schema capability proposals (including a future model-proposed plan) are rejected before ever becoming a `PlanStep` — `CapabilityPlanner` only ever consults the registry, never trusts caller-declared risk or arguments. Disabled capabilities are inert: `validateStep` refuses them with the same `capabilityUnavailable` failure whether the caller is a human utterance or a hypothetical automated planner. No new adapter accepts free-form executable model text; the four still-`.disabled` capabilities have no adapter at all yet, so there is nothing to accidentally execute.

## Operational impact

`AuraKernel.construct()` now builds and registers the capability registry alongside every other subsystem, recording readiness in `RuntimeHealthRegistry`. `ToolRouter`'s public API changed (`registry: ToolRegistry` → `capabilityRegistry: CapabilityRegistry`); every construction site (`AuraKernel`, `ToolRouterTests`, `EndToEndPipelineTests`, `AuraAdversarialTests/Fakes.swift`) was updated in the same pass — zero behavioral regression, verified by the full existing suite passing unchanged.

## Validation evidence

- `CapabilityRegistryTests` (`Tests/AuraIntentTests/CapabilityRegistryTests.swift`): fail-closed unknown ID and wrong version, latest-version resolution, re-registration overwrite, reachable-vs-disabled filtering, the full initial set's truthful disabled reasons, locale fallback.
- `CapabilityPlannerTests` (`Tests/AuraIntentTests/CapabilityPlannerTests.swift`): unknown/model-proposed capability rejection, disabled-capability rejection, missing/empty required argument rejection, risk-tier recomputation from the registry (not the caller), multi-step dependency ordering, plan-too-large rejection, self/forward dependency cycle rejection, fingerprint stability for identical steps and divergence for different arguments.
- `ToolRouterTests`, `DialogueEngineTests`, `EndToEndPipelineTests`, `AuraAdversarialTests` — all pre-existing suites — pass unchanged after the registry migration, proving zero regression to the five already-production capabilities.
- Full repository regression: 20/20 Swift Testing bundles, no failures, after every change in this ADR.

## Known gaps carried forward (honestly, not silently)

- `filesystem.open_file`/`open_folder`/`reveal` and `url.open` have real, reviewed manifests but no adapter — genuinely new work for a follow-up pass, not claimed done here.
- The four newly `.ready` capabilities (`app.discover`, `app.hide`, `task.status`, `task.cancel`) are reachable only through direct `AuraKernel` calls, not yet through the bilingual utterance classifier or any UI control — no live/UI test exercises them yet.
- The planner's `PlanResult` cases (`.directAnswer`, `.clarification`, `.multiStepPlan`, `.delegatedTask`, `.refusal`) are implemented and unit-tested as building blocks; `ToolRouter`/`DialogueEngine` do not yet call through the planner for automatic multi-step decomposition from free-form natural language — that requires model-backed planning, explicitly out of scope for this pass.
- R2's two blockers (`RISK-STT-MIC-NOT-CAPTURING`, residual `RISK-STRUCTURED-NLU-MODEL-QUALITY` sampling variance) remain open by explicit user choice; R3 work proceeded in parallel per that instruction, not because R2 was resolved.

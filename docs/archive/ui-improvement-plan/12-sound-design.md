# UI-V: Sound Design — Sonic Identity

**Volume:** I — Identity & Foundations.
**Status:** Design proposal, gated behind a user decision. Sound is the only axis in the plan that adds a *new sensory channel* to the product; it is adopted or rejected as a whole in the UI-0 ADR. Nothing here changes any behavioral path.
**Implements:** Design Vision Pillar 4 ([08-design-vision.md](08-design-vision.md)).

---

## 1. Current state (verified)

AURA is silent. No sound assets exist in the repo (no `.caf`/`.aiff`/`.wav` in `Resources/`, no `AVAudioPlayer`/`NSSound` usage in `Sources/AURA/` beyond capture/playback of the voice pipeline itself). The only audio the user hears is their own voice and the TTS response. This is a *gap in feedback*, not just an opportunity: today the transition into/out of listening is carried entirely by a small visual pill, which is invisible when the user is not looking at the screen — precisely the moment a voice agent matters most.

## 2. Sonic thesis: "instrument contact"

A precision instrument makes one kind of sound: **contact**. A soft, glassy grain — like a fingertip touching laboratory glass — marks the moment a state *engages*. No melody, no voice, no musical motif. The set is defined by one timbre, differentiated only by pitch and length, so the ear learns the whole vocabulary from two exposures.

- **Timbre:** single synthesized glass-grain (sine + short filtered noise burst, exponential decay) — generated, not sampled, so the entire set is regenerable from one script with zero licensing surface.
- **Palette:** all earcons derived from the same base grain; pitch mapping follows the visual status palette (idle/biolume low, critical high) so sound and color agree.

## 3. The earcon set

| Event | Earcon | Duration | Rationale |
| --- | --- | --- | --- |
| Wake / PTT press-in | single grain, mid pitch | ≤ 120 ms | "Contact." The most-used sound; must be nearly invisible |
| Listening open (status → listening) | grain, slightly brighter | ≤ 180 ms | Confirms capture actually started (mic permission granted, device live) — an *honest* signal, not decoration |
| Thinking | none | — | Silence is the thinking state; the visual arc carries it |
| Speaking (TTS start) | none | — | The voice itself is the signal; an earcon before speech is an interruption |
| Response delivered | low soft grain | ≤ 200 ms | Only if TTS is off (text-only mode); omitted when TTS speaks |
| Confirmation required | two grains, amber pitch | ≤ 250 ms | Must be distinct from every routine sound; paired with the visible card |
| Confirmation granted | resolving grain | ≤ 150 ms | Closes the challenge loop |
| Restricted / degraded | single grain, low | ≤ 200 ms | Paired with amber pill; never a scolding buzz |
| Error | grain, lowest pitch | ≤ 200 ms | Paired with red text; no alarm clichés |
| **Emergency stop** | **hard stop grain** | ≤ 250 ms | The one authoritative sound — clipped, wideband, unambiguous. Never melodic, never soft here |

Forbidden: speech beeps before/after TTS, notification-style dings, success fanfares, idle sounds of any kind, loops. If a state has no entry in the table, it is silent.

## 4. Integration design (additive)

1. **`AuraEarconChannel`** (new file, `Sources/AURA/`): a thin `NSSound`-based player (no `AVFoundation` dependency needed at this scale) fed by the existing `AuraEventBus` — it subscribes to the same events the UI already consumes (`StatusChangedEvent`, `ConfirmationRequestedEvent`, error paths) and is therefore *causal by construction*: if the state change did not happen, no sound plays.
2. **Assets:** generated by a new `scripts/generate-earcons.sh` (the same generator philosophy as the icon pipeline in [10 §4](10-icon-identity.md): vector→deterministic asset, nothing hand-exported); output `.caf` files into `Resources/sounds/`; bundled alongside existing resources.
3. **Preference:** a single `ProductUIState` field `soundFeedbackEnabled` (default **off** until evaluated live — sound ships dark, like any new sensory surface); exposed in Settings (UI-4, General category) with real EN/TR copy keys.
4. **Latency contract:** earcons fire from the event bus on the main actor with no added pipeline work; nothing in the voice path waits on sound. The emergency-stop earcon must never delay the stop itself (sound is fire-and-forget; the stop path is untouched).

## 5. Accessibility pairing rules (mandatory)

- **Every earcon is paired with a visual state change** that already exists (pill, card, badge). No information exists only in sound — this is the audio analogue of the color-never-alone rule.
- **System alert setting respected:** earcons route through a path that honors the system's alert volume; if the system is muted, AURA is silent — never a separate volume universe.
- **VoiceOver coexistence:** earcons are suppressed while VoiceOver is running (they would collide with spoken UI); VoiceOver users get the state changes through announcements, which the plan already guarantees.
- **Reduce Motion has no sound analog** but the same principle applies: no sound may be the only carrier of a transition.

## 6. Verification and acceptance

- Unit: `AuraEarconChannel` maps each event to at most one earcon; disabled preference yields zero player calls (pure logic test, no audio hardware).
- Bundle: `.caf` assets present in `Contents/Resources/sounds/`.
- Live: each earcon heard once per state transition in a scripted PTT turn; confirmation challenge pair verified in the live gate; emergency stop sound verified *after* the stop took effect (order assertion in the driver run).
- Silence audit: a full onboarding pass and an idle hour produce **zero** sounds (grep of the driver event log).

## 7. Risks

| Risk | Mitigation |
| --- | --- |
| Sound becomes annoyance after weeks of use | Default off; wake grain is the only high-frequency sound and is ≤ 120 ms; per-user kill switch |
| Earcons collide with TTS audio on the same output device | Earcons only on non-TTS events; pre-TTS sounds forbidden (§3); volume ducking not needed |
| Sound pipeline adds latency to event handling | Channel is a passive subscriber; zero writes to the bus, zero reads from the capture path |
| Licensing/originality | Entire set synthesized by the repo's own script; no third-party audio |

## 8. Decision point

Adopting sound is a product decision, not a design detail — the UI-0 ADR records it as adopt-now / adopt-later / reject. Recommendation: **adopt-later** — land the vocabulary and the preference scaffolding with UI-0 (cost ≈ 0), evaluate the synthesized set on the reference machine, and decide with ears, not on paper.

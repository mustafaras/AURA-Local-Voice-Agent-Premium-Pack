## Finding: the grant scoping was inert on any existing installation

The first live run (16:36–16:41Z) executed five scripted turns. Two results mattered:

| Turn | Trace outcome | Reading |
|---|---|---|
| `open file /tmp/aura-sp006-rerun-20260816/note.txt` | `tool.result filesystem.open_file` → **verified** | in-root open still works |
| `open file /etc/hosts` | `tool.result filesystem.open_file` → **failed** | refused — but by the *adapter*, not policy |

The absence of a `policy` phase row for the `/etc/hosts` turn is the tell: `handleFileOpen` returns before emitting `ToolInvoked`/`ToolResult` when policy blocks, so a `tool.result` row proves **policy allowed it** and only `OpenTargetValidator`'s new `approvedRoots` stopped it. The unit test `fileOutsideDeclaredRootsDenied` asserted a policy denial and passed — so the test and the live system disagreed.

Cause, read from the store itself (`~/Library/Application Support/AURA/aura.db`, key `aura.policy.grants`, 216 KB):

- **895 persisted grants.** `issueGrant` de-duplicates by `id`, and `Grant` mints a fresh `UUID` per construction, so seeding in a loop appended a complete new copy of the default set on **every launch** since 2026-07-27.
- **30 of them were pre-scoping `.any` grants** for `file.open` / `file.reveal` / `url.open`.
- `matchingGrant` returns `grants.first { … }`, so a legacy `.any` grant matched before any newly scoped `.directory` grant and authorized exactly the path the scoping was written to refuse.

The SP-006 follow-up's target scoping was therefore **correct in tests and inert in the field** — the worst shape a security fix can take. It would have protected only a machine that had never run an older build.

## Fix

- `DefaultPolicyGrants.seedPurpose` (`"aura.default-seed"`) now stamps every seeded grant.
- New `PolicyEngine.reconcileSeededGrants(_:marker:)` **replaces** the seeded set instead of appending. It prunes, in order: every grant carrying the marker; every *legacy* grant matching the pre-marker seed signature (empty purpose, `patterns == [.any]`, a governed capability); and every grant whose shape (capability + patterns + confirmation) is identical to one about to be installed, so an intermediate build's unmarked-but-scoped grants cannot survive as permanent duplicates. It returns the prune count.
- `AuraKernel.seedDefaultGrants` calls it once and logs the migration whenever it removes standing authority.

Grants outside those three signatures are untouched — a narrower or purposeful grant from any other path survives, which `reconcilePreservesOtherGrants` pins.

## Cognitive completion gate

1. **Symptom:** `/etc/hosts` reached the adapter live although the policy test said policy would deny it.
2. **Mechanism / root cause / layer:** persistence layer — seeding appended a fresh copy of the default set per launch (895 accumulated), and 30 legacy `.any` grants for the filesystem/URL capabilities preceded the scoped grants in `matchingGrant`'s first-match scan.
3. **Direct change:** marker-stamped seeds + `reconcileSeededGrants` (marker / legacy-shape / redundant-shape pruning) + kernel migration logging.
4. **Evidence ID / class:** this record — direct live system evidence, three launches, with trace rows and the store inventory.
5. **Falsifier:** any post-migration launch where the persisted grant count exceeds `DefaultPolicyGrants.all.count`, an unmarked leftover survives, `/etc/hosts` yields a `tool.result` row instead of a policy denial, or an in-root open stops working.
6. **Residual risk:** `url.open` fails on this machine and always has (pre-existing, now documented); the `quit` confirmation difference is unexplained; scenarios 4–7 not re-run live; declared roots remain a fixed list.
7. **Why this is safe to stop here:** the confinement is enforced at the policy layer on a real, previously-polluted store, proven live and reproduced across two launches, with the grant set settling at exactly the seeded size.

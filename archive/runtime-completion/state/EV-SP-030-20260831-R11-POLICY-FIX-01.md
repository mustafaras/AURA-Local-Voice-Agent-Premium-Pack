This is **authority, not review**. It authorizes the change; it is not a

## What was changed

### 1. The missing grant (`Sources/AuraPolicy/DefaultPolicyGrants.swift`)

```swift
Grant(
  capability: .lifecycleLaunchAtLogin, patterns: [.any],
  confirmationRequirement: .forRiskTier(.mutation), purpose: seedPurpose),
```

`.forRiskTier(.mutation)` rather than `.none`, matching `.appTerminate` in the
same file: enabling launch-at-login writes a persistent, system-level login
item, so the user confirms the *effect*. A `.none` grant would have worked
without touching the presenter at all — it was offered and not chosen, because
it lets a grant stand in silently for the user's intent.

**This is the SP-006 finding recurring one track later**, and the file's own
header documents that earlier instance: capabilities registered `.ready`,
implemented, and wired into the composition root, but denied before reaching
their adapter because nothing seeded a grant. The same shape went unnoticed
again for the lifecycle family.

### 2. The presenter, wired (`Sources/AURA/AuraKernel_RuntimeAPI.swift`)

`evaluateDirectCapability`'s `.confirm` arm threw. It now runs the same
present-then-submit cycle `ToolRouter_Policy` already uses:

```swift
let response = await confirmationPresenter.present(challenge: challenge)
guard case .allow = await policyEngine.submitConfirmation(response) else {
  throw AuraError.permissionDenied("… was not confirmed")
}
```

The security properties are unchanged and are not being taken on trust:
`submitConfirmation` re-derives the decision and verifies nonce, expected hash
and expiry, so a forged or replayed response authorizes nothing. Anything other
than `.allow` still fails closed. The previous `throw` was a correct default —
the defect was that it was the *only* behaviour, leaving every
confirmation-requiring capability unreachable on the path the capability
registry names as their access route.

### 3. The false reason string, corrected (`Sources/AuraIntent/InitialCapabilitySet_CapabilityDefinitions.swift`)

The registry disabled all eleven lifecycle capabilities citing *"reachable
through direct AuraKernel RuntimeAPI calls"*. That was false for nine of them.
The string now states which are actually reachable and says plainly that the
rest are not, so it can no longer assert a guarantee the code does not provide.

## Scope — deliberately one capability, not nine

Only `lifecycleLaunchAtLogin` is seeded. Safe mode, reset, rollback, uninstall,
factory reset and update check/stage/approve remain **deny-by-default**, on the
same reasoning the file already applies to `task.delete`: they are
`.destructive` or `.network` tier and each needs authorizing on its own terms.
Fixing one control's reachability is not a licence to open the rest, and a fix
that quietly widened eight destructive capabilities would have been a worse
defect than the one it repaired.

## Tests — including the one whose absence caused this

The full suite passed **with the original defect present**. 1317 tests contained
none asserting that a lifecycle capability was reachable by a user, which is
precisely how a registered, implemented, composition-root-wired control shipped
unusable. Three tests added to
`Tests/AuraPolicyTests/DefaultPolicyGrantsTests.swift`:

| Test | Asserts |
|---|---|
| launch at login is reachable, and asks for confirmation | `.confirm`, **not** `.deny` — the toggle reaches the OS |
| the destructive lifecycle capabilities stay deny-by-default | all eight still `.deny` |
| exactly one lifecycle capability is seeded | pins the scope of the widening |

A fourth change was forced rather than chosen: the pre-existing
`grantInventoryIsExact` **failed** when the grant was added. That test exists to
alarm on any widening of the seeded set, and it did its job; it was updated
deliberately, with the reason recorded inline, rather than being weakened.

## What is NOT yet proven — the important limitation

**Everything above is `deterministic_harness`.** The policy decision is now
`.confirm` instead of `.deny` *in a test-constructed engine built from the
unmodified production `PolicyConfiguration`*. That is a strong signal, and it is
not the same claim as:

- the confirmation card actually appearing in the running app;
- the user accepting it and `SMAppService` being reached;
- the login item actually being registered with the OS;
- the toggle reading back enabled afterwards, and surviving a reboot.

**No live verification has been performed.** The signed `/Applications/AURA.app`
still contains the pre-fix binary, so the live reproduction recorded in
`EV-SP-030-20260831-R11-POLICY-BLOCK-01` remains the current observed behaviour
of the installed app. R11's live gates are **not** closed by this record. Until
a live run exists, the honest statement is *"the policy layer no longer denies
it"*, never *"launch at login works"*.

Any of the following would falsify this record: that `lifecycleLaunchAtLogin`
still evaluates to `.deny` under the production configuration; that any of the
eight destructive/network lifecycle capabilities became reachable; that
`submitConfirmation` is bypassed, or that an unverified or expired response can
authorize; that the seeded set contains more than one lifecycle capability; that
this constitutes a live verification, a sign-off, or closure of R11's live
gates; or that the installed application currently contains this fix.

## Finding 1 — the planner was not on the production path

**Symptom:** `grep -rn "CapabilityPlanner(" Sources/` returned nothing. `CapabilityRegistry` was
used from `ToolRouter_ToolRouter.swift`, `IntentEngine_IntentEngine.swift`, and
`AuraKernel_Construction.swift`, but the planner — the type whose doc comment promises "only a
manifest-validated step ever becomes a `PlanStep`" — was constructed solely in tests.
`ToolRouter` resolved a contract and dispatched straight to a handler.

**Change:**

- `ToolRouter` now owns a `CapabilityPlanner`, built in `init` from the registry it already
  holds, so no call site changed.
- `route(_:executionContext:dialogueContext:)` builds a validated single-step plan through
  `planSingleCall` before dispatch. A missing required slot is now refused by the planner rather
  than by a handler, and an `IntentBlockedEvent` records which argument was missing.
- `IntentPlanGeneratedEvent` gained `planFingerprint`, so "a validated plan existed before
  anything executed" is observable in the trace instead of only asserted in a test.
- New `ToolRouter.routePlan(_:context:)` executes a validated multi-step `Plan`. Steps run in
  index order — `buildPlan` already rejects any dependency that does not point strictly
  backward, so index order is a valid topological order. A step whose dependency did not execute
  is recorded `.skipped`, never attempted.
- `IntentDispatchCoordinator.executePlan(steps:context:)` and `AuraKernel.executePlan(steps:)`
  expose this. The coordinator owns the router privately, so routing multi-step execution
  through it keeps the planner mandatory instead of widening router ownership.

**Deliberately not claimed:** execution is not transactional. Steps that already ran keep their
effects, and `PlanExecutionReport` carries each step's manifest `rollbackStrategy` verbatim
rather than implying an undo occurred.

## Finding 2 — neither layer confined a filesystem target

`RISK-SP-006-DEFAULT-GRANT-BREADTH` was registered saying refusal "rests entirely on
`OpenTargetValidator`". Closing it showed that **understated** the exposure: every production
site built the opener via `OpenTargetValidator()`'s default `approvedRoots: []`, which the type
documents as *no root restriction*. The validator's executable-extension, sensitive-fragment, and
scheme rules were real, but nothing bounded where a target could live — and the policy layer's
`patterns: [.any]` bounded nothing either.

**Change** — both layers now read one shared declaration, `AuraCore.DeclaredFileRoots`:

- Policy: `.fileOpen`/`.fileReveal` granted per root as `.directory(root, recursive: true)`. One
  grant per root is required, not stylistic: `patternsSatisfied` demands *every* pattern in a
  grant match, while `matchingGrant` accepts the first grant that does, so alternatives must be
  separate grants.
- New `ResourcePattern.urlScheme(allowed:)` scopes `url.open` to the adapter's allowlist.
  `.network(host:port:)` could not express this — a `mailto:` URL has no host, so host-scoping
  would refuse legitimate mail links while still permitting `file:` or `ftp:`.
- Adapter: all three production construction sites now pass `OpenTargetValidator.production`.
  The bare `init()` keeps the permissive default so focused tests supply their own sandbox and
  production confinement must be stated explicitly rather than inherited.
- `DeclaredFileRoots` lists both the raw and canonicalized spelling of each root, because the
  policy layer compares raw strings while the adapter canonicalizes — `NSTemporaryDirectory()`
  reports `/var/folders/…` for a directory that canonicalizes to `/private/var/folders/…`.

A target outside the roots is now refused twice for independent reasons: a raw-prefix policy
check before the adapter is reached, and `PathConfinement`'s canonicalized component-wise check
inside it, which still catches a `..`/symlink escape the string comparison would miss.

Adding the enum case made the compiler enumerate every consumer: exhaustive switches in
`PolicyEngine_Evaluation`, `PluginRuntime.permissionAllowed`, and
`PluginManifest.canonicalDescription` all had to handle it. The plugin sites follow that file's
existing fail-closed posture, and the manifest canonicalization uses the established
`name:value` shape so previously canonicalized manifests hash identically.

## Scope and limitations

- **No live re-run.** This is source + test evidence. The confinement and planner changes alter
  production behavior, and the seven scenarios have not been re-run live under the new posture.
  That is the honest gap in this record.
- **Natural-language multi-step decomposition remains unwired** — explicitly outside the scope
  the user selected. The structured-NLU layer still proposes at most one capability per turn, so
  no user sentence produces a multi-step plan; `routePlan`/`executePlan` require a caller to
  supply the steps. Recorded in `capability-matrix.json` under
  `intent.capability_registry.open_gaps`.
- The declared roots are a fixed built-in list, not a user-managed setting. A user whose files
  live outside home and the temp directories will be refused until a grant-management surface
  exists (R9/R10). Fail-closed by choice.
- `implementation_state` for `intent.capability_registry` therefore stays `partial`.

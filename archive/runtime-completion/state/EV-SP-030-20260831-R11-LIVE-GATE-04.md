## Why this record exists

`EV-SP-030-20260831-R11-LIVE-GATE-03` left the live click-through unverified
because the display had powered off. This session resumed with the display
awake and the user actively present, and made an extended, escalating series of
attempts to complete the live click-through via accessibility (AX) automation.
None converged. This record states plainly what was tried, what was found —
including one significant positive finding at the OS level — and why the
automated approach was abandoned rather than continued indefinitely.

## The positive finding: `SMAppService.register()` has succeeded at least once

Ground truth, independent of the app's own AX state, from macOS's Background
Task Management:

```
$ sfltool dumpbtm
 #1:
   Name: AURA
   Type: app (0x2)
   Disposition: [disabled, allowed, notified] (0xa)
   Identifier: 2.ai.aura.local.agent
   URL: /Applications/AURA.app
```

AURA is **registered** with BTM. `disabled` means it is not currently set to
launch at login, but the registration itself is proof that `service.register()`
— a real macOS API call, not a mock — executed successfully at some point in
this session. `notified` confirms the system already surfaced the standard "X
was added to login items" system notification for it.

This corroborates the live click made in `EV-SP-030-20260831-R11-LIVE-GATE-01`:
that session *did* accept a confirmation card and the write *did* reach
`service.register()`. At the time, the readback appeared to fail
("AFTER=0") — but the read path was, at that point, gated by the same
`.mutation` confirmation as the write (the bug LIVE-GATE-02 fixed), so the
read-back call itself was silently denied and never queried the true OS state.
The write likely succeeded then and the *readback*, not the write, was what
failed. This is a materially stronger piece of evidence for the mechanism
working than anything recorded so far.

## What was attempted this session, and what it found

An extended series of hardened AX-automation attempts to complete a clean,
scripted click → confirm → readback cycle against the current build (with the
inline Settings card from `LIVE-GATE-03`). In order:

1. **A Unicode string-matching defect in the test script itself**, found and
   fixed: AppleScript's `is` (exact string equality) unreliably matched the
   Turkish label `"Girişte AURA'yı başlat"` — `contains` on the same string
   worked. Root cause not conclusively identified (suspected Unicode
   normalization form mismatch between the AX-returned string and the
   AppleScript literal); switching to a purely ASCII substring (`"te AURA"`)
   made the *value* comparison reliable.
2. **`position of` intermittently throws for specific elements**, independent
   of the matching fix. The label's own position lookup failed even when its
   *value* was read correctly moments earlier in the same window state.
3. **Switching to checkbox-position-based targeting** (topmost `AXCheckBox` by
   Y-coordinate, bypassing the flaky label lookup entirely) worked in one
   isolated diagnostic call, then failed in the very next call with an
   identical query against the same window.
4. **The whole element tree intermittently reports zero `AXCheckBox` /
   `AXSwitch`-role elements**, even though `entire contents of window`
   returns the same total element count (~61) as calls where the checkboxes
   *were* found. This points to the SwiftUI `Form`'s AX tree being
   regenerated frequently enough that a query can land between a teardown and
   a rebuild.
5. **The window itself intermittently reports `-1728` ("Can't get window")**
   moments after a call that had just successfully confirmed its existence,
   consistent with the focus-loss behaviour already documented in
   `EV-SP-030-20260831-R11-LIVE-GATE-01/02`, but occurring even without an
   explicit `activate` in between.

None of these are the product defect this track has been chasing — each
earlier product defect (contaminated `ptt_ack`, the read/write confirmation
conflict, the invisible main-panel card) was found *because* automation
surfaced a real, reproducible, position-independent symptom. This is
different: the same script, run twice in a row with nothing else changing,
returns different results. That is the signature of test-tooling flakiness,
not application behaviour, and no further evidence in this record should be
read as suggesting otherwise.

## Decision: stop automating this specific check

After the fourth escalating hardening pass (Unicode-safe matching, retry loops,
`AXRaise`, avoiding redundant `activate` calls, checkbox-position-only
targeting) still did not produce two consecutive successful runs, continuing
was judged to have a poor cost/signal ratio relative to a five-second manual
click. This is a judgment call, stated plainly rather than disguised as
completion.

## What this does NOT change

R11's live gate is **still not formally closed** — a clean, reproducible,
automated end-to-end demonstration does not exist as of this record, even
though the OS-level evidence for the mechanism is now stronger than at any
prior point in this program. No SLO measured, no scenario re-run, no sign-off
obtained, no gate moved. SP-030 stays `blocked`; SP-031 must not start.

## Recommendation for the next session or the owner directly

A single manual click — Settings → *Girişte AURA'yı başlat* → accept the card
that appears **in the Settings window** → confirm the toggle reads on → check
System Settings → General → Login Items — would resolve the one remaining
uncertainty in under a minute, at a fraction of the cost this session spent
fighting AX-tree flakiness. If instead another automated attempt is preferred,
the fixes above (ASCII-only substring matching; checkbox-position rather than
label-position targeting; expect and retry through `-1728`) should be applied
from the start rather than rediscovered.

## Falsifiers

Any of the following would falsify this record: that `sfltool dumpbtm` does
not show AURA registered; that the toggle is not currently OFF; that a clean
automated click-through **was** in fact reproduced and this record wrongly
claims otherwise; or that R11's live gate is closed by this record (it is not).
